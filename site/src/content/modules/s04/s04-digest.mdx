A web server in 1999 obeyed one rule that nobody questioned. One connection gets one worker. A worker was a process, then a thread, and for ten years good engineers made that worker cheaper. In 2002 an engineer at a large Russian portal asked a different question. His servers failed under the number of connections that did nothing at all, not under the number of requests. Why does a sleeping connection need a worker?

This class is the answer to that question, followed into the real nginx source. It matters because almost every web request today passes through a proxy of this shape. Each line of an nginx config is one small, readable piece of that machine. When you can read the machine, you can say what a config does before you deploy it.

**The path through this read.** Part 1 walks the ten years of cheaper workers and the question that ended them. Part 2 puts one loop on each CPU core and shows what that loop forbids. Part 3 gives the kernel two jobs: to watch the sockets, and to move the file bytes. Part 4 puts nginx in front of your servers, with a cache behind it. Part 5 reads the surface that you configure: which block answers a URL, and which server gets the next request.

<Picture breaks="a waiter costs a salary, and a process costs memory, a scheduler slot and a context switch. The lobby is a list inside the kernel, and a restaurant has nothing like it.">

A restaurant gets busy. First it hires one waiter for each guest who comes in. Then it hires a team before it opens. Then the waiters share one locker room, but each waiter still stands at one table. Last, a host seats the resting guests in the lobby and calls a waiter only for an order. Every step makes a waiter cheaper, and nobody asks whether a resting guest needs a waiter at all.

Each waiter is a worker: a process, and later a thread. Each guest is a connection, and a guest who reads the menu for ten minutes is an idle connection. The lobby with the host is the kernel, which holds the quiet connections and names the ready ones.

</Picture>

<KeyIdea id="nginx-deleted-the-worker" title="nginx deleted the worker, it did not make it cheaper">

From 1993 to 2002 every new server design answered one question: how do we make the per-connection worker cheaper? nginx answered a different question. One idle connection needs only a small state record, a few hundred bytes, plus one slot in a list. It needs no process and no thread.

</KeyIdea>

CGI, from 1993, paid for a whole program start on every request: fork, exec, the load of an interpreter, a parse, the run, and the exit. Prefork moved that fork to startup, but one process still sat on one connection for its whole life. Threads made the worker lighter in the Apache 2.0 worker MPM, and the Apache 2.4 event MPM parked idle keep-alive connections on epoll, the list of ready sockets that the kernel keeps for you, and woke a thread only for real work. Part 3 opens that list. All three designs answered the same question. The same move appeared on the application side with another name: a servlet from 1997 loads one time, each request is a method call on a pooled thread, and a connection pool does this for the database handshake. FastCGI does the same for CGI, because it keeps one program alive between requests. The one goal was to stop the creation of a process.

Dan Kegel named the C10K problem in 1999: ten thousand concurrent connections on one box. By 2002 the hardware was ready and the software was not. A Linux thread got an 8 MB stack by default, every connection got a scheduler entry, and the 1983 `select` API stopped at 1024 descriptors. So the goal of nginx was ten thousand mostly idle connections in one process, with another program to make the dynamic pages. That single choice is the reason nginx is a reverse proxy.

Two ideas transfer to your own work. When everybody improves the same part, look one level higher: Apache tuned the worker, and nginx asked why the worker existed. And check whether a constraint still exists: a goroutine starts at 2 KiB, so Go brought thread-per-connection back. The order of the designs shows which rules are laws and which are habits.

<Myth myth="Berners-Lee wrote Mosaic, and Mosaic became Apache.">

Three different programs hide in that sentence. The first web server was CERN httpd, written by Berners-Lee on a NeXT machine in 1990. Mosaic was a browser from NCSA in 1993, by Andreessen, and it brought inline images and made the web popular. Apache descends from NCSA HTTPd, a second NCSA program. That one was a server, and it invented CGI.

</Myth>

<Remember>

- CGI pays fork, exec, interpreter load, parse, run and exit on every request.
- Apache 1.3 prefork forks its pool at startup. One process still parks on one connection.
- The Apache 2.4 event MPM parks idle keep-alives on epoll. Unix default since 2.4.
- A servlet object loads one time. Each request is a method call on a pooled thread.
- Prefork, FastCGI, servlets, pools and upstream keep-alive: pay the setup one time.
- In 2002 the hardware was ready. A stack and a scheduler entry per connection were the limit.
- 10,000 idle connections in one process, with another program for the dynamic pages. So nginx is a proxy by design.
- An idle connection needs a small state record and one slot in a list.
- The first public nginx release is 4 October 2004.
- Two ideas that transfer: ask the other question, and check whether the constraint still exists.

</Remember>

<Picture breaks="a nurse can leave a task when the alarm rings. Nothing interrupts a handler here, so a handler must never wait inside its task. It saves its place, it returns, and the loop calls it again on the next event.">

A night nurse has a board of call buttons and an alarm clock. Before she rests, she sets the alarm for the next medicine time. She wakes when a button lights or when the alarm rings. She answers every lit button, she gives the medicine that is due, she sets the alarm again, and she rests.

The nurse is one worker process, and her floor is one CPU core. The board of call buttons is the kernel list of ready sockets, and each lit button is a connection with data. The alarm clock is the timer tree, and the next medicine time is the nearest deadline.

</Picture>

<KeyIdea id="one-loop-one-thing-at-a-time" title="One loop, one thing at a time">

A worker is one process with one event loop. It sleeps in a single call until the kernel reports a ready socket or the nearest deadline arrives. Nothing may wait inside that loop, so every parser in nginx must stop at any byte and continue later.

</KeyIdea>

The master process reads the config, binds port 80 as root, forks one worker per core, and drops the workers to an unprivileged user. After that the master only handles signals. It never touches a client connection, and a worker never forks again. So the process count of nginx does not change under load. The teaching program `forkd` and nginx both call `fork()`. Only the rate differs, and the whole story from 1994 to 2004 sits in that difference.

The loop itself is six lines. Ask the timer tree for the nearest deadline. Sleep in `epoll_wait` with that deadline as the limit. Run the queued accept events. Release the accept mutex. Fire every timer that is due. Run the other queued events, and start again. A timeout therefore costs nothing while nothing times out, because nginx never polls for one. The nearest deadline is the leftmost node of a red-black tree. The deck says on <SlideLink session={4} page={12} /> that a worker spends 99.9% of its life asleep in line 2. That figure is a teaching number, not a measurement.

Each worker also decides alone when to stop taking new connections. It computes `accept_disabled = connection_n / 8 - free_connection_n`. Past 7/8 of its slots the value turns positive, and the worker gives its siblings the next connections. There is no leader, no heartbeat and no shared counter. Each worker reads a number that it already holds. The `accept_mutex` that made this work is off by default since version 1.11.3. In 2004 one new connection woke every worker, which was a real problem, and a userspace mutex fixed it. `EPOLLEXCLUSIVE` on Linux 4.5 and `SO_REUSEPORT` moved the fix into the kernel, so the mutex lost its reason and became dead weight.

Now the price. A handler cannot wait for the rest of a request, so the HTTP parser is a state machine that resumes. It holds 27 states for the request line alone, it reads one byte at a time, and it uses no regular expression, no substring and no allocation. It saves `r->state` between calls, because a request line can arrive in three TCP segments. That is the source-level cost of non-blocking input and output, and a thread-per-connection server can simply wait until the blank line. The request resumes in the same way. Eleven phases run in a four-line loop. First POST_READ and SERVER_REWRITE, then FIND_CONFIG, then REWRITE and POST_REWRITE, then PREACCESS, ACCESS and POST_ACCESS, and last PRECONTENT, CONTENT and LOG. On <SlideLink session={4} page={31} />, a return from that loop means "suspended", not "done", and the deck calls the engine a coroutine, hand-rolled in C. `limit_req` runs in PREACCESS, `auth_basic` in ACCESS, `try_files` in PRECONTENT, and `proxy_pass`, `fastcgi_pass` and the static handler in CONTENT. Only the static handler sits in the CONTENT handler array. `proxy_pass` and `fastcgi_pass` set the content handler of their own location, so a grep of the phase arrays never lists them.

<Beyond source="nginx 1.31.5, ngx_event.c and ngx_event_accept.c" url="https://nginx.org/en/docs/ngx_core_module.html#accept_mutex">

The loop reads `accept_disabled` only while `accept_mutex` is on. With the default off on Linux, a positive value instead makes the worker add its listen socket back, so `EPOLLEXCLUSIVE` wakes a sibling for the next connection. The 7/8 rule holds either way, by two different routes.

</Beyond>

<Remember>

- One process per core, one loop in each. No connection owns a thread or a process.
- The master binds the ports, reads the config, forks the workers and handles signals. Never a connection.
- The worker count does not change under load. fork happens at startup and on reload.
- Six lines: nearest timer, epoll_wait, accept events, release the mutex, expire timers, other events.
- The epoll_wait timeout is the nearest deadline, the leftmost node of a red-black tree.
- "99.9% asleep" is a teaching number, not a measurement.
- accept_disabled = connection_n / 8 - free_connection_n. Positive past 7/8 full.
- No coordinator. Each worker reads a number that it already has.
- accept_mutex is off by default since 1.11.3, because EPOLLEXCLUSIVE and SO_REUSEPORT do the job.
- The request-line parser: 27 states, one byte at a time, no allocation.
- `r->state` survives between reads, because a line can arrive in three segments.
- That state machine is the source-level cost of non-blocking I/O.
- Eleven phases, POST_READ to LOG. A return can mean "suspended", not "done".
- limit_req PREACCESS, auth_basic ACCESS, try_files PRECONTENT, static CONTENT. proxy_pass sets its own location handler.

</Remember>

<Picture breaks="a card can outlive its student. If one student leaves and a new student takes the same seat number, the teacher reads the old card and answers the wrong person. nginx puts a coloured sticker on every seat and changes the colour for each new sitter, so a card with the wrong colour goes in the bin.">

A teacher has 10,000 students. With the old method she reads the whole register every minute, and every student answers "nothing" or "question". That is 10,000 answers to find 10 questions. With the new method a student with a question drops a card in a box, and she reads only the cards. The second trick is the same move. The office used to send worksheets to her desk, and she carried each sheet to the student. Now the office puts them straight on the desk of the student, and no sheet passes through her hands.

The register is the `select` bitmap, which your process rebuilds on every call, and the box of cards is the epoll ready list inside the kernel. The worksheets are file bytes, her desk is your buffer in user space, and the direct delivery is `sendfile`. Each seat number is a file descriptor.

</Picture>

<KeyIdea id="move-the-work-into-the-kernel" title="Both big wins move work into the kernel">

epoll gives the kernel the watch list, so one call costs the ready sockets and not the watched ones. sendfile gives the kernel the file bytes, so they never enter your process. In both cases the win is the work that you no longer do.

</KeyIdea>

`select` keeps its watch list inside your process and rebuilds it on every call, so it costs O(watched): O(n) to build the bitmap, O(n) in the kernel, and O(n) to scan the answer. epoll keeps the list in the kernel, `epoll_ctl` edits it one time per socket, and `epoll_wait` copies out only the ready events, so it costs O(active). With 10,000 idle sockets and 10 active ones, `select` does about 30,000 units of work to find 10 events, and epoll does 10. Every other difference follows from that one decision about who owns the list. `ulimit -n` does nothing for `select`, because `FD_SETSIZE` is a bitmap width of 1024 fixed in a header, and it does everything for epoll.

epoll brings one trap. `epoll_wait` returns a batch of events. When you handle event 1, you can close the connection that event 7 points at. A new client can then land on the same recycled descriptor, and event 7 reaches the wrong connection. Every author of an event loop writes this bug one time. nginx stores an instance flag in the low bit of the connection pointer, flips the flag when it reuses the connection, and skips an event whose flag does not match. Structs are aligned, so that low bit is always zero. The flag costs no memory and one branch.

The second move is about bytes, not sockets. A `read()` and a `write()` make four copies and two mode switches for each chunk: disk to page cache, page cache to your buffer, your buffer to the socket buffer, socket buffer to the network card. One `sendfile()` call names the file and the socket, and the data never enters your process. With a network card that has scatter-gather DMA and checksum offload, both copies that stay are DMA copies. Bytes that you must change have to come into user space, so gzip and TLS force the file bytes into memory. That is why gzip and sendfile fight, and why kTLS exists, which moves the encryption itself into the kernel. `sendfile on` is a permission, not an order.

<Myth myth="sendfile makes every transfer faster.">

On the instructor laptop over loopback, a 64 MB file took 37.4 ms with read plus write and 33.2 ms with sendfile. That difference is not the win. Over loopback there is no network card and no DMA, the kernel copies into the receiver buffer in every mode, and `curl` competes for the same CPU. What really changed is the syscall count: 2,048 calls became 1, and 64 MB never entered the process. When a benchmark does not model the real bottleneck, it measures the wrong thing.

</Myth>

<Remember>

- select costs O(watched). epoll costs O(active).
- The select list lives in your process, rebuilt each call. The epoll list lives in the kernel.
- select: O(n) build, O(n) in the kernel, O(n) scan. epoll: O(ready events).
- 10,000 idle and 10 active: about 30,000 units against 10.
- ulimit -n does nothing for select and everything for epoll.
- Every row of the comparison follows from one decision: who owns the watch list.
- A batch can name a connection that an earlier handler in the same batch closed.
- nginx keeps an instance bit in the low bit of the connection pointer, and skips a mismatch.
- Alignment keeps that bit zero, so the flag costs no memory and one branch.
- read plus write: 4 copies, 2 mode switches per chunk. sendfile: 2 copies, both DMA, 0 switches.
- True zero copy needs a card with scatter-gather DMA and checksum offload.
- gzip and TLS must see the bytes, so they stop sendfile. Hence kTLS.
- On any machine, 2,048 syscalls become 1, and the 64 MB never enters the process. Headroom, not speed.
- A benchmark that misses the real bottleneck measures the wrong thing.

</Remember>

<Picture breaks="the department sees only the desk. It learns who the visitor was from the note, and a visitor can write a false line in that note.">

A campus librarian who fetches books for students and keeps copies is a forward proxy. The front desk of a company is a reverse proxy. Visitors talk only to the desk. The desk listens to a slow visitor for as long as it takes, writes one clean note, and gives it to the right department in one second. Behind the desk stand a card catalogue and the book stacks. A stamp says whether a book is current, a dust rule removes a book that nobody borrowed for a minute, and a shelf limit forces the oldest book out even when it is current.

The slow visitor is a phone on a 2G link, the department is your application server, and the note is the buffered request. The line that a visitor can forge is the `X-Forwarded-For` header. The card catalogue is the cache index in shared memory and the stacks are the files on disk, so the stamp is `proxy_cache_valid`, the dust rule is `inactive`, and the shelf limit is `max_size`.

</Picture>

<KeyIdea id="the-proxy-absorbs-the-slow-client" title="A reverse proxy absorbs the slow client">

A reverse proxy is the same caching machine as a forward proxy, moved to the other side. Its quiet superpower is that it holds the slow phone, so your application does not. Behind it, the cache keeps a small index in shared memory and the bodies in files on disk.

</KeyIdea>

Squid, from 1996, is a forward proxy next to the clients. It caches for a campus and protects the uplink. A reverse proxy is the same machinery on the opposite side: it caches, routes, balances, moves to another server on a failure, terminates TLS, and holds slow clients. The client does not configure it and usually cannot see it, so a reverse proxy can do things that a client would never agree to. The feature lists leave out the one that matters most. A phone that needs 10 seconds to read a response would hold an application worker for 10 seconds, and at 100 requests per second that is 1,000 busy workers. With nginx in front, the app answers in 20 ms, so 100 times 0.02 gives 2. The 1,000 idle connections move to nginx, where a connection is cheap.

The cache is two structures. An index lives in shared memory, and the bodies live in files on disk. `keys_zone=demo:10m` reserves 10 MB for the red-black tree and the LRU queue, at about 8,000 keys per MB, so about 80,000 keys. It sizes the index, not the data. `max_size=100m` is the disk ceiling, and the cache manager deletes from the LRU tail to stay under it. Three clocks run at the same time. `proxy_cache_valid` says how long a stored answer stays fresh. `inactive=60s` deletes an entry that nobody read for 60 seconds, whatever its freshness. And a full cache deletes the least recently used entry even when it is fresh. On <SlideLink session={4} page={20} />, eviction is one check on the tail: a young tail ends the pass, and an old tail that no client reads is deleted. The test `count == 0` stops a delete while a client downloads that file. Add `X-Cache-Status` from `$upstream_cache_status` to every cache config, and two calls to `curl` show MISS and then HIT.

Two switches handle the stampede. `proxy_cache_lock` is the anti-stampede switch, and it is off by default. Without it, a popular object that expires sends every request of the next 200 ms to the origin. With it, one request goes and the rest wait. `proxy_cache_use_stale` with `error`, `timeout`, `updating` and the 5xx codes serves the old copy in place of an error. With `updating`, one request refreshes the entry and everybody else gets the stale copy at once.

<Beyond source="nginx 1.31.5 source and the proxy module docs" url="https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_lock">

In the 1.31.5 code the lock covers a new cache element, which is a MISS. The instructor's own config comment agrees and says "on a miss". For an entry that expired, the first request refreshes it and `updating` gives the stale copy to the others. So both lines belong in a real config.

</Beyond>

<Remember>

- Squid sits next to the clients. A reverse proxy sits next to the servers. Same machinery, opposite side.
- The client does not configure a reverse proxy and usually cannot see it.
- The feature that nobody lists: a reverse proxy absorbs slow clients.
- Connections held = request rate times time held. Buffering moves the wait off the app.
- The cache is an index in shared memory plus bodies in files on disk.
- keys_zone sizes the index, about 8,000 keys per MB. max_size caps the disk.
- inactive measures time since the last read. proxy_cache_valid measures freshness.
- The whole eviction policy on <SlideLink session={4} page={20} />: a young tail ends the pass, an old tail with no reader is deleted.
- count == 0 stops a delete while a client downloads that file.
- The cache manager evicts from the LRU tail. The cache loader warms the index.
- proxy_cache_lock is the switch against a stampede. It is off by default.
- proxy_cache_use_stale serves a stale copy on error, timeout, updating and 5xx.

</Remember>

<Picture breaks="in nginx the exact addresses sit inside the same prefix tree, so there is only one walk and not two.">

A post office sorts a letter by its address. First a clerk checks a short list of exact addresses, and a hit ends the sort at once. Then the clerk walks a tree of street prefixes and remembers the longest street that fits. A "no detours" flag on that street ends the sort. If not, the clerk reads a list of pattern rules from the top, and the first pattern that fits wins. With no pattern at all, the remembered street wins.

The address is the URI, and the short list of exact addresses is the `=` locations. The tree of streets is the prefix locations, which nginx builds one time when it reads the config, and the "no detours" flag is `^~`. The list of pattern rules is the regex locations, in the order of your file.

</Picture>

<KeyIdea id="the-data-structure-is-the-rule" title="The data structure is the documentation">

nginx keeps prefix locations in a tree and regex locations in a plain array. A tree can report the longest match cheaply. An array can report only the first match in order. Those two facts are the whole precedence rule.

</KeyIdea>

Location precedence does not follow the order in which you wrote the blocks. An `=` location is an exact match, and it wins at once. A `^~` location is a longest prefix that suppresses the regex search. A `~` location is a regular expression, and the first match in file order wins, not the longest one. `~*` ignores case. A plain prefix such as `location /` answers only when no regex matched. On the class config at port 8081, `/exact` gives 1, `/images/a.php` gives 2, `/other/a.php` gives 3, and `/anything` gives 4. About half the room gets `/images/a.php` wrong and expects the regex to win. The reason is the structure: prefixes form a ternary search tree that nginx builds at config parse time, and regexes form a plain array that it walks in order on every request. So 500 prefix locations are cheap and 500 regex locations are not.

The same reading works on the choice of an upstream server. Smooth weighted round robin adds the weight of each server to its current weight, picks the largest current weight, then subtracts the total of all weights from the winner. For weights 3 and 1, <SlideLink session={4} page={24} /> writes the result as `a b a a`: the same ratio as the naive `a a a b`, with the turns of the heavy server spread apart. A failure lowers the effective weight of a server, and each selection raises it back by one. That is passive health checking, with no probe traffic. Open-source nginx has no active health checks, and NGINX Plus sells them.

The last piece is the directive behind almost every web framework. `try_files $uri $uri/ /index.html?$args` asks three questions in order: is there a real file, is there a real directory, and if not, hand the request to the app. The last entry is never tested. It is the fallback, not a candidate. `try_files $uri @app` tries the disk first and then the upstream, and only `try_files` or `error_page` can reach a named location such as `@app`. A URL never reaches one. WordPress, Rails, Django and every single-page-application router are this one directive plus an app that reads `REQUEST_URI`.

## Reading the machine

One skill survives every release of nginx. Line numbers drift and function names do not, so find a function by its name at the start of a line. nginx puts the return type on its own line, which makes that search exact. Three protocol trees, `src/http`, `src/stream` and `src/mail`, sit on one shared core, and the repetition is the argument for the design. nginx never frees the memory of a request piece by piece. It allocates from a pool that belongs to the request and destroys the whole pool at the end, so the hot path has no `free()`, no refcounting and almost no cleanup branches. Each of the 100 or more modules has the same four parts: a directive table, config callbacks, the module struct, and handlers in a phase. The callbacks are eight functions that create and merge configs, and `merge_loc_conf` decides what a location inherits from its server. The class ladder is seven small servers in the instructor repo, and each one adds the next fix: `01-fork`, `02-thread`, `03-select`, `04-epoll`, `05-sendfile`, `06-fastcgi` and `07-nginx`. That repo is about 1,200 lines and nginx is about 200,000, and the difference is every error path. The full lesson is <ModuleLink id="s04-m12-reading-the-source" />.
