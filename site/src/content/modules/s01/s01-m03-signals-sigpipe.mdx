A server is a program that waits for other programs, its clients, to connect over the network, and then answers them. Picture your server as it runs well for hours. Then one client leaves in the middle of an answer, and your server is gone. It printed no error, and it left no line in a log. What killed it? This lesson answers that question.

The killer is a **signal**, a short message that the kernel sends to a program that runs. The kernel is the core of the operating system. This signal is called SIGPIPE. The kernel sends it when a program keeps writing to a connection that the other side already ended. By default, SIGPIPE ends the program at once, and the program prints nothing. A server in C meets this trap as soon as one real client leaves early. The calculator assignment of this course asks you to write a server, so the trap is close.

If you start here, you need a few more ideas. The server never uses the network itself. It asks the kernel with system calls, which are requests from a program to the kernel. `write()` sends bytes to the client, `read()` gets bytes from it, and `close()` ends the connection. The connection follows TCP, the set of rules that the kernel uses to carry bytes in order. You type commands in a terminal window, and the program there that runs your commands is the **shell**. On Linux, the usual shell is bash. The lesson <ModuleLink id="s01-m01-seven-syscalls" /> shows the system calls in full. The top of the page also names a thread, a big idea that comes back in many lessons. This thread says that a call over the network is not like a call to a function in your own program. It can fail halfway, because the other side can vanish.

**The path through this lesson.** Part 1 runs the class demo: a server dies, prints nothing, and leaves only the number 141. Part 2 explains signals, and that number points to the killer, SIGPIPE. Part 3 looks inside: how the client hangs up the hard way, and which write of the server brings the signal. Part 4 shows two ways to keep a server alive, and you try each setting in a simulator.

<SignalBoard slot="visual" />

<Picture breaks="a child hears each call and can ask why. A process that made no plan for a signal gets the rule of the kernel at once, and for SIGPIPE that rule ends the process.">

A teacher watches the playground, and every child knows the calls of the teacher. A child can have a plan for a call. The teacher is the kernel, and each child is a **process**, a program that runs. Each call is a **signal**, a short message with a name and a number. A plan for a call is a **handler**, code that the program runs when that signal arrives. Programmers say that the handler catches the signal. A plan to take no notice is to ignore the signal. "Recess is over" is SIGTERM: a process can catch it, finish its work, and then end. "Freeze" is a signal that pauses a process, so that it can go on later. Being carried inside is SIGKILL: no handler can catch it. The rule for a child who keeps throwing to nobody is SIGPIPE. It ended the server in Part 1.

</Picture>

### How it works

A signal interrupts a process in the middle of its work. Some signals come from you, such as Control-C in the terminal. Others come from another program, or from the kernel itself, as SIGPIPE does. The signal from Part 1 ended the server because the server set up nothing for it.

<Beyond source="signal(7), Linux man page" url="https://man7.org/linux/man-pages/man7/signal.7.html">

Each signal has a **default action**: what the kernel does when the process asked for nothing else. For most signals, SIGPIPE too, the default action ends the process. A process can ask for something else. It can set a **handler**, its own code that runs when the signal arrives, or it can ignore the signal. Two signals allow neither: no process can catch or ignore SIGKILL or SIGSTOP.

</Beyond>

<KeyIdea id="sigkill-cannot-be-caught" title="No program can catch SIGKILL">

A program can catch most signals and run its own code for them. SIGTERM, the polite kill, lets the program clean up first. No program can catch SIGKILL.

</KeyIdea>

When a signal ends a process, the shell shows 128 plus the number of the signal as the exit status. So a status over 128 usually means that a signal ended the process. A program can also exit with such a number by itself, but the class server has no line that does that.

<KeyIdea id="exit-status-141-means-sigpipe" title="Exit status 141 means SIGPIPE">

When signal N ends a process, the shell shows the exit status 128 + N. SIGPIPE is signal 13, so 141 − 128 = 13. The server of Part 1 died by SIGPIPE.

</KeyIdea>

Try it on the board next to this text. Pick SIGPIPE and keep the default. Then pick SIGKILL and set a handler, and see that the handler does not help. Last, type 141 into the exit status reader.

### The real thing

The slide on signals warns that SIGPIPE is "the one that will kill you" <SlideLink session={1} page={12} />. It gives four numbers. Signal 2 is SIGINT, which Control-C sends. Signal 9 is SIGKILL, which no program can catch. Signal 13 is SIGPIPE, for a write to a peer that closed. The peer is the other end of the connection. Signal 15 is SIGTERM, the polite kill. The same slide adds SIGHUP, which a process gets when its remote terminal connection, SSH, drops. It also names SIGSTOP and SIGTSTP next to Control-Z. The name SIGPIPE and the words "Broken pipe" come from pipes, a way to join two programs in a shell. Part 4 shows a pipe. A write to a dead connection gets the same signal. The README of the class repo explains 141 as 128 plus SIGPIPE, 13.

<ExamDepth>

- **The polite kill first.** SIGTERM lets a process finish its work and close its files. SIGKILL gives it no chance. So a careful stop sends SIGTERM, waits, and sends SIGKILL only if the process does not end.
- **Exit status arithmetic.** 130 means SIGINT, 137 means SIGKILL, 141 means SIGPIPE and 143 means SIGTERM. Each one is 128 plus the signal number. A run in bash on Linux 7.1.8 gave all four, and 129 for SIGHUP (2026-09-14).

<Beyond source="signal(7) and kill(1), Linux man pages" url="https://man7.org/linux/man-pages/man7/signal.7.html">

On Linux on x86 and ARM computers, SIGHUP is signal 1, SIGSTOP is 19 and SIGTSTP is 20. Control-Z in a terminal sends SIGTSTP. It pauses the process and does not end it, and a program can catch it. SIGSTOP also pauses a process, but like SIGKILL, it cannot be caught. The command `kill` asks the kernel to send a signal to a process by its ID. With no signal named, as in `kill 1234`, it sends SIGTERM. `kill -9 1234` sends SIGKILL.

</Beyond>

<Beyond source="Bash Reference Manual, Exit Status" url="https://www.gnu.org/software/bash/manual/html_node/Exit-Status.html">

The rule of 128 + N belongs to the shell. When a command ends on a fatal signal N, bash uses 128 + N as its exit status.

</Beyond>

<Segment title="A reset, then the write that kills">

**In this part.** Part 2 named the killer, SIGPIPE. This part shows how the demo sets the trap. You learn the two ways that a program can close a TCP connection, and why the client of the demo picks the hard way. Then you see which write of the server brings the signal on Linux.

<ResetLanes slot="visual" />

<Picture breaks="a ball flies over the wall on each throw. On the first write, the kernel of the server sends no byte at all. It only reports the reset that it already got.">

Your friend can leave the game of catch in two ways. The nice way: your friend shouts "I am done, bye!" and goes home. The hard way: your friend just runs off and drops the ball in their hands. Either way, your friend catches no more balls. When you throw after the hard way, a neighbor shouts back: "Nobody is there!" If you throw again anyway, the teacher sends you inside.

Leaving the nice way is a normal `close()`, which sends **FIN**: I send no more data. Leaving the hard way sends **RST**, a reset: the connection ends now, and bytes that wait to be sent are dropped. The shout of the neighbor is the error of your first write. The teacher who sends you inside is SIGPIPE, on your second write. After a nice close, the side that closed first also waits for a set time, in a state called TIME_WAIT. The playground has nothing like that wait.

</Picture>

### How it works

A normal `close()` sends FIN. After both sides close, the side that closed first waits in TIME_WAIT for a set time. The class client does not close that way. A socket is the handle that a program holds on its end of a connection, and a socket option changes how the kernel treats it. Before `close()`, the client sets the option SO_LINGER to `{1, 0}`. The 1 turns lingering on, and the 0 sets a linger timeout of zero, so people call it linger 0. With linger 0, `close()` sends RST instead. The connection ends at once, unsent bytes are dropped, and no side waits in TIME_WAIT.

<KeyIdea id="linger-zero-sends-rst" title="Linger 0 closes with RST, not FIN">

A normal `close()` sends FIN, and the side that closes first waits in TIME_WAIT. With SO_LINGER set to `{1, 0}`, `close()` sends RST: the connection ends at once, unsent bytes are dropped, and nobody waits in TIME_WAIT.

</KeyIdea>

Now follow the demo from inside, on Linux, with both programs on one computer. Scroll through the steps.

<ScrollStep step={1}>

The client sends `hello`. The 5 bytes wait in the kernel of the server until the server reads them.

</ScrollStep>

<ScrollStep step={2}>

Right after that, the client sets linger 0 and calls `close()`. Its kernel sends RST, not FIN, and the client program ends.

</ScrollStep>

<ScrollStep step={3}>

The RST reaches the kernel of the server, and the kernel marks the connection as reset. It still keeps `hello` for the server. On one computer, the reset usually arrives before the server even reads.

</ScrollStep>

<ScrollStep step={4}>

The server calls `read()` and gets the 5 bytes. The read gives no sign of the reset. Then the server calls `sleep(1)`, which makes sure that the reset is in before the writes.

</ScrollStep>

<ScrollStep step={5}>

</ScrollStep>

<ScrollStep step={6}>

The server calls `write()` again. Now the connection can send nothing at all. The write returns -1 with the error EPIPE, "broken pipe", and the kernel sends SIGPIPE to the server.

</ScrollStep>

<ScrollStep step={7}>

</ScrollStep>

<KeyIdea id="write-after-reset-kills" title="A write after a reset kills the process">

On Linux, the first write after a reset fails with the error ECONNRESET. The next write fails with EPIPE, and the kernel sends SIGPIPE. Its default action ends the process with no error message.

</KeyIdea>

### The real thing

The slide of the server code says in its title that the second write never runs <SlideLink session={1} page={13} />. Its comments put SIGPIPE on the first write. A run on Linux shows a small difference. The tool `strace` prints each system call of a program, with its result after the `=` sign. After an error, `strace` also prints the meaning of the error in brackets, such as "(Connection reset by peer)". This page leaves those words out, so that the lines fit. Here is `strace` of the server with the class client (Linux 7.1.8, loopback, 2026-09-14):

```
read(4, "hello", 4096) = 5
write(4, "hello", 5) = -1 ECONNRESET
write(4, "hello", 5) = -1 EPIPE
--- SIGPIPE {si_signo=SIGPIPE, ...} ---
+++ killed by SIGPIPE +++
```

The number 4 is the file descriptor of the connection, the number that the server uses to name it. The first write fails with ECONNRESET and brings no signal. The second write does run. It fails with EPIPE and brings SIGPIPE, and the server dies inside it. So on Linux, the call after the second write never runs. Nobody checked macOS for this page. On a quiz, expect the wording of the slide.

The client slide shows linger 0 <SlideLink session={1} page={14} />: a `struct linger` with the values `{1, 0}`, then `setsockopt()` with `SO_LINGER`, then `close()`. The second class comes back to it <SlideLink session={2} page={5} />. A normal close sends FIN, and the socket waits in TIME_WAIT for 2 MSL. The closed box below explains MSL. Linger 0 sends RST, drops unsent data and leaves no TIME_WAIT. The slide calls linger 0 fast and lossy: good to show the difference, not for production. A run on Linux 7.1.8 over loopback agreed (2026-09-14). After a normal close, the client socket sat in TIME_WAIT. After a linger 0 close, no socket did.

<ExamDepth>

- **A read never brings SIGPIPE.** In the demo, the read still returns the 5 bytes that wait. A copy of the server with two more reads showed the rest: the next read returned -1 with ECONNRESET, and the read after it returned 0 (Linux 7.1.8, loopback, 2026-09-14). Only a write brings SIGPIPE.
- **FIN or RST.** FIN says "no more data from me", and the side that closes first keeps TIME_WAIT. RST aborts: it drops unsent data and leaves no TIME_WAIT. Linger 0 is for demos.

<Beyond source="net/core/stream.c, sk_stream_error(), Linux kernel source" url="https://github.com/torvalds/linux/blob/master/net/core/stream.c">

**Why ECONNRESET first?** On Linux, a reset stores an error on the connection. When a TCP send fails, Linux first returns that stored error, ECONNRESET. It sends SIGPIPE only when the error is EPIPE, and never when the call passes the flag MSG_NOSIGNAL, an option of `send()` that Part 4 shows. After the reset, the connection can send no more, so every later write gets EPIPE and SIGPIPE.

</Beyond>

<Beyond source="RFC 9293 §3.4.2 and §3.6.1, and include/net/tcp.h in the Linux source" url="https://www.rfc-editor.org/rfc/rfc9293#section-3.6.1">

MSL means maximum segment lifetime: the longest time that the TCP standard expects a packet to stay in the network. The standard takes it as 2 minutes, and the side that closes first waits 2 MSL in TIME_WAIT. Linux uses a fixed 60 seconds for TIME_WAIT (`TCP_TIMEWAIT_LEN` in `include/net/tcp.h`).

</Beyond>

</ExamDepth>

**In this part.** Part 3 showed the trap: one client that leaves can kill the whole server. A real server serves many clients, so it must survive that. <KeepAlive slot="visual" />

<Picture breaks="in the story, you stop after one shout. A server keeps writing to the dead connection until its own code checks the error and closes that client.">

Your parents write a note to the teacher: "If our child throws a ball to nobody, just say so. Please do not send our child inside." Now a throw to nobody gets only a shout: "Nobody is there!" You stop throwing to that friend, and you play with the next friend in line. You can also make a smaller ask. Before one throw, you tell the teacher: "For this throw only, just tell me."

The note from home is one line at the start of the server, `signal(SIGPIPE, SIG_IGN)`, which ignores SIGPIPE for the whole process. `send()` is a write for a socket, with room for options called flags. The ask for one throw is the flag `MSG_NOSIGNAL` on one call to `send()`. The shout is the error that the write returns. Playing with the next friend is closing that one client and serving the next one.

</Picture>

### How it works

<Beyond source="send(2) and signal(7), Linux man pages" url="https://man7.org/linux/man-pages/man2/send.2.html">

A server can stop SIGPIPE in two ways. The first way works for the whole process: call `signal(SIGPIPE, SIG_IGN)` one time, at the start. The second way works for one call: use `send(fd, buf, n, MSG_NOSIGNAL)` in place of `write()`. Either way, the write still fails and returns -1, with the error ECONNRESET or EPIPE. So the server checks the result of each write. On an error, it closes that one client and goes on with the others.

</Beyond>

Try it in the simulator next to this text. The first setting is the class demo, and the server dies. Change one choice at a time. Find every setting that keeps the server alive, and look at which write fails in each one. On one computer, a normal close does not save the server. The first write works. But the client program already ended, so its kernel answers those bytes with RST, and the second write brings SIGPIPE.

<Beyond source="pipe(7), Linux man page, and the GNU C Library manual, Operation Error Signals" url="https://man7.org/linux/man-pages/man7/pipe.7.html">

**Why is this signal useful at all?** It also works for pipes. A pipe joins two programs in a shell. In `cat big.log | head`, the program `cat` writes a large file into the pipe. The program `head` prints the first 10 lines and ends, so nobody reads the pipe any more. The next write of `cat` brings SIGPIPE, and `cat` stops at once, with no code for it. A run on Linux 7.1.8 gave `cat` the exit status 141 (2026-09-14). For `cat`, stopping is right, because nobody wants the rest of the file. For a server with many clients, the same default is a trap, so a server turns it off.

</Beyond>

### The real thing

The client of the demo can die the same way. Run `./05_sigpipe_client` with no server. Its `connect()`, the call that asks the kernel to reach a server, fails and returns -1. The error is ECONNREFUSED, "connection refused", because no server waits on that port. The code checks nothing and calls `write()` on a socket with no connection. That write fails with EPIPE and brings SIGPIPE, so the client also ends with 141. Here is `strace` of the client alone, with the meanings of the errors left out (a copy on a spare port, Linux 7.1.8, loopback, 2026-09-14):

```
connect(3, ...) = -1 ECONNREFUSED
write(3, "hello", 5) = -1 EPIPE
--- SIGPIPE {si_signo=SIGPIPE, ...} ---
+++ killed by SIGPIPE +++
```

So an exit status of 141 alone does not prove that the server demo worked. Run the server first, and ask `wait` for the status of the server.

<ExamDepth>

- **One dead client, one error.** With SIGPIPE turned off, a server that checks each write closes only the client that failed. Every other client keeps its connection.

**If you see 0 and "Done".** Your shell ignores SIGPIPE, and a program that a shell starts keeps an ignored signal ignored. Some tools start a shell that way. Run the demo in a normal terminal window.

The first lines of `strace` load the program, so look for the lines with the number 4, the connection. You see one read of 5 bytes, a write with ECONNRESET, and a write with EPIPE. Then you see the SIGPIPE line and `+++ killed by SIGPIPE +++`.
