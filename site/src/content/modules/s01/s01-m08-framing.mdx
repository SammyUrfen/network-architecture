<InventFirst prompt="Design a chat app where a message can hold any byte, even a newline. How does the receiver know where one message stops?">

Three rules work. Part 2 of this page shows that the first rule is a length rule too.

1. **Fixed length.** Every message has the same size, N bytes. A short message gets padding.
2. **Delimiter.** A special byte ends each message. When the data holds that byte, the sender must escape it.
3. **Length prefix.** The sender writes the byte count first, then the bytes.

</InventFirst>

### How it works

1. The sender writes `hello`, then `world`.
2. TCP puts the 10 bytes in its send buffer. It can send them in one segment or in several.
3. The receiver reads. It can get `hel` and then `loworld`, or all 10 bytes at once.
4. Nothing in TCP marks the edge between the two writes.
5. So the protocol adds the edge: a length that it knows, a delimiter that it scans for, or a length prefix that it reads first.

### The real thing

The persistent echo server of Session 1, `02_echo_server_persistent.c`, calls `read()` again and again on one connection. Each call asks for up to 4096 bytes and returns the count that it got. The server writes that many bytes back.

An echo server needs no framing, because it only copies bytes back. A chat server or a calculator must know where each message ends. After Part 3, a predict block asks what this server reads.

<Beyond source="read(2), Linux man page" url="https://man7.org/linux/man-pages/man2/read.2.html">

The man page says that a short count is not an error. `read()` can return fewer bytes than the buffer holds, for example when fewer bytes wait on a socket.

</Beyond>

<ExamDepth>

- **The reader keeps leftovers.** A read can stop in the middle of a message. It can also hold the end of one message and the start of the next. So the reader keeps the unused bytes for the next message.
- **The buffer size is not a message size.** The echo server asks for 4096 bytes. A read gives what waits, from 1 byte up to 4096 bytes. Only end of file gives 0.

</ExamDepth>

### How it works

**Fixed length.**

1. Both sides agree on N before the connection starts. The protocol spec holds N, not each message.
2. The sender pads a short message to N bytes.
3. The reader counts N bytes. Those bytes are one message.

**Delimiter.**

1. Both sides agree on an end byte, such as a newline.
2. The sender writes the message, then the end byte.
3. The reader scans for the end byte. The bytes before it are one message.

<ExamDepth>

- **Three answers or two?** Slide 39 gives three rules. Session 2 slide 41, Session 3 slide 18 and Session 5 slide 16 say "length or delimiter", with no third option. Both statements hold. A fixed length is a length that both sides agreed on before the connection started. It lives in the spec, not in each message.
- **The cost of a fixed length.** The parse is trivial, and nothing is ambiguous. But every short message pays for padding, and N can never change.
- **The cost of a delimiter.** A delimiter is readable, and the sender needs no size up front. But the sender must escape the delimiter when the data holds it. SMTP adds a dot to a body line that starts with a dot (<ModuleLink id="s02-m07-smtp-mime" />).
- **Text or binary.** Slide 38 says text won: a person can read it with telnet, tcpdump and logs, and that is most of why HTTP won. The class notes add that text is easy to debug, and that SMTP splits a mail with delimiters. Text is also verbose, ambiguous at the edges and slow to parse. Binary is compact and cheap to parse, with no whitespace rules and no case-sensitivity arguments. The notes say binary suits places where speed and efficiency matter. Its cost is tools: you need a hex dump to read it. HTTP/1.1 is text, and HTTP/2 is binary.
- **Are TCP/IP headers fixed length?** The class notes call them fixed size, and say that variable-length messages are more common today. The headers have a fixed part plus a length field. So even a "fixed" header carries a length.

<Beyond source="RFC 791 §3.1 (IPv4 IHL), RFC 9293 §3.1 (TCP Data Offset)" url="https://www.rfc-editor.org/rfc/rfc9293#section-3.1">

The IPv4 header and the TCP header each have a fixed part of 20 bytes. Options can follow. A length field in each header, IHL in IPv4 and Data Offset in TCP, gives the header size in 32-bit words.

</Beyond>

</ExamDepth>

### How it works

1. The sender counts the bytes of the message.
2. It writes the count in a field of fixed width, such as 1 byte. Then it writes the bytes.
3. The reader reads the count first. Then it takes exactly that many bytes as one message.

The reader never scans the data, so the data can hold any byte. That is why slide 39 calls the length prefix binary-safe.

### The real thing

The same 301 response on slide 17 carries `Content-Length: 219`. After the empty line, the reader takes exactly 219 bytes of body and stops. The body of that response is exactly 219 bytes.

A binary protocol puts the length in bytes, not in text. Here a 2-byte length, big-endian, says 5, and then `hello` follows.

Slide 39 calls the length prefix robust, binary-safe, and "what most modern protocols do".

<ExamDepth>

- **Field width.** A 1-byte length caps a message at 255 bytes. 2 bytes cap it at 65,535 bytes, and 4 bytes at about 4 GB. A wider field costs more bytes on every message.
- **The cost of each rule.**

| Rule | Good | Cost |
|---|---|---|
| Fixed length | trivial parse | padding, and N can never change |
| Delimiter | readable, no size needed up front | escape the delimiter in the data |
| Length prefix | binary-safe, no scan | the sender must know the size first, and the field width caps it |
| Both | readable control lines, a safe binary payload | two parsers, two ways to fail, and request smuggling in the gap (Session 2 slide 36, Session 5) |

- **Redis in two decks.** Slide 47 calls RESP "text and length-prefixed". Session 2 slide 36 lists Redis under delimiter. Both decks hold, because RESP uses both rules.

<Beyond source="Redis serialization protocol specification, sections Bulk strings and Sending commands" url="https://redis.io/docs/latest/develop/reference/protocol-spec/">

The command `LLEN mylist` crosses the wire as `*2\r\n$4\r\nLLEN\r\n$6\r\nmylist\r\n`. Each `$N` gives the byte count of the next part, and CR LF ends each line. The diagram frames the three messages of Part 2 in the same way.
