Your program sends "hello" and then "world" over TCP. The other program can get "helloworld" in one read, or "hel" and then "loworld". So how does it know where one message ends? This lesson answers that question.

TCP is the part of the operating system that carries bytes between two programs, complete and in order. A protocol is the set of rules that the two programs follow. Without a rule for the end of a message, a server mixes two requests into one, or it waits for bytes that never come. The calculator assignment turns on this idea, and so does the binary HTTP project. From the lesson <ModuleLink id="s01-m01-seven-syscalls" />, you know that a program sends bytes with `write()` and gets bytes with `read()`. That is all you need to start.

**The path through this lesson.** Part 1 shows that TCP keeps every byte in order but forgets where each message stopped. Part 2 gives two different answers to that problem: make every message the same size, or put a marker after each message. Part 3 gives the answer that most modern protocols use: send the length before the bytes. At the end, you watch a real server read two sends, and you check what you learned.

<Segment title="A byte stream has no edges">

**In this part.** You learn why the program that reads cannot see where one message ends and the next one starts. Every later part of this lesson solves this one problem, so it comes first.

<Animation slot="visual" name="stream" title="Two writes, one stream, and reads that cut anywhere" />

<Picture breaks="a real string can snap and drop beads with no sign. TCP never gives the reader a gap or a wrong order. If it cannot deliver the bytes, the connection fails with an error.">

Your friend makes two bead bracelets for you and sends them in a thin tube. To fit the tube, your friend puts all the beads on one long string, one bead after the other. At home, you take the beads from the string a handful at a time. One handful can hold the last beads of the first bracelet and the first beads of the second. Nothing on the string shows where the first bracelet stopped.

In TCP, each bead is a byte, and each bracelet is a message. The long string is the connection. Your friend is the program that sends, and each call to `write()` adds beads to the string. You are the program that receives, and each call to `read()` takes one handful. A read can return any number of bytes, from 1 up to the space that the program gives it. So the two programs must agree on a rule before they start, and Part 2 gives the first two rules.

</Picture>

### How it works

The animation follows these steps as you scroll. You can also press Play, or step with the buttons.

<ScrollStep step={1}>

The sender calls `write()` with the five bytes of hello. Each letter of hello is one byte.

</ScrollStep>

<ScrollStep step={2}>

The sender calls `write()` again, with world. The animation still shows a gap after hello, but that gap exists only inside the program that sends.

</ScrollStep>

<ScrollStep step={3}>

TCP puts all ten bytes on one stream, in order, like beads on the string. The gap is gone. From here on, nothing marks where hello ended.

</ScrollStep>

<ScrollStep step={4}>

TCP sends the stream over the network in pieces called segments. TCP picks the size of each segment, and the program cannot set it directly. A segment can hold part of one write, or the end of one write and the start of the next. TCP does not wait until its buffer is full. It usually sends a small write at once, but it can hold one for a moment while earlier bytes wait for a reply from the other side (<SlideLink session={5} page={28} />).

</ScrollStep>

<ScrollStep step={5}>

The receiver calls `read()` to take bytes, one handful at a time. A read returns the bytes that wait at that moment. Here the first read gets hel, and the second read gets loworld.

</ScrollStep>

<ScrollStep step={6}>

Run the same two programs again, and the cuts can land in other places. This time the reads get hellow and orld.

</ScrollStep>

<ScrollStep step={7}>

When both programs run on one computer, one read can get all ten bytes: helloworld. In every run, the bytes arrive complete and in order. In no run can the receiver see where hello ended.

</ScrollStep>

<KeyIdea id="tcp-keeps-order-not-edges" title="TCP keeps the order, not the edges">

TCP delivers every byte, in order. It keeps no mark where one write stopped. So one read can hold part of a message, or parts of two, and the program must find where each message ends.

</KeyIdea>

### The real thing

The echo server of Session 1 shows the loop that every reader has. The lab at the end of this lesson shows where to get its code. The server calls `read()` again and again on one connection. Each call gives `read()` a buffer, a space of 4096 bytes, so one call can return up to 4096 bytes. The call returns the count of bytes that it got, and the server writes that many bytes back.

An echo server needs no framing, because it only copies bytes back. A chat server or a calculator must know where each message ends.

<Beyond source="read(2), Linux man page" url="https://man7.org/linux/man-pages/man2/read.2.html">

The man page says that a count smaller than the buffer is not an error. It can happen because fewer bytes are available at that moment.

</Beyond>

<ExamDepth>

- **The reader keeps leftovers.** A read can stop in the middle of a message. It can also hold the end of one message and the start of the next. So the reader keeps the unused bytes for the next message.
- **The buffer size is not a message size.** The echo server asks for up to 4096 bytes. A read gives what waits, from 1 byte up to 4096 bytes. A read that returns 0 means that the other side closed its sending side: the stream has ended.

</ExamDepth>

<Segment title="Two answers: fixed length or a delimiter">

**In this part.** Part 1 left one question: where does a message end? This part gives two different answers to it: make every message the same size, or put an end marker after each message. Each answer has a cost, and Part 3 gives the answer that most modern protocols pick.

<Animation slot="visual" name="rules" title="The same three messages, framed two ways" />

<InventFirst prompt="Before you read on, try it. You build a chat app, and a message can hold any byte, even the newline byte that ends a line of text. How does the receiver know where one message stops?">

Two kinds of rule work. The first kind marks the end: an agreed byte, the delimiter, follows each message. A chat message can hold that byte, so the sender must change that byte in the data. The second kind gives the size. Every message can have the same agreed size, a fixed length. Or the sender can write the size before each message, a length prefix. This part covers the fixed length and the delimiter. Part 3 covers the length prefix.

</InventFirst>

<Picture breaks="a person can see that a red bead in the middle of a pattern belongs to the pattern. A program cannot guess, so it ends the message at the first delimiter byte.">

Your friend sends more bracelets on one string, and this time you agree on a rule first. One rule is this: every bracelet has exactly 10 beads. For a short bracelet, your friend adds plain wooden beads at the end to make 10. You count 10 beads, and that is one bracelet. The other rule is this: a big red bead ends each bracelet. You slide beads off the string until you meet a red bead.

In framing, the count of 10 is the fixed length, which a protocol calls N bytes. The wooden beads are pad bytes, filler that means nothing. The red bead is the delimiter, an agreed byte such as a newline. The first rule counts, and the second rule looks for a marker. So they are two different answers to one question.

</Picture>

### How it works

<ScrollStep step={1}>

**Fixed length.** Both sides agree on a size N before the connection starts. The rules of the protocol hold N, so no message needs to carry it. In the animation, N is 5. The sender adds pad bytes to hi and to abc, so each message is exactly 5 bytes.

</ScrollStep>

<ScrollStep step={2}>

The reader counts 5 bytes, and those bytes are one message. Then it counts the next 5 bytes. It never looks at what the bytes say.

</ScrollStep>

<KeyIdea id="fixed-length-is-an-agreed-length" title="A fixed length is a length agreed ahead of time">

With a fixed length, every message is N bytes, and both sides agree on N before they start. The reader counts N bytes, so it needs no end marker. The length is still there. It lives in the rules of the protocol, not in each message.

</KeyIdea>

<ScrollStep step={3}>

**Delimiter.** This time, both sides agree on an end byte, such as a newline. A newline is the invisible byte that ends a line of text, written `\n`. The sender writes each message, then a newline. No message needs pad.

</ScrollStep>

<ScrollStep step={4}>

The reader checks one byte at a time. When it meets a newline, the bytes before it are one message. So the reader learns the size of a message only when it finds the end.

</ScrollStep>

<ScrollStep step={5}>

Each answer has a cost. A fixed length spends bytes on pad: in the animation, 5 of the 15 bytes are pad. A message longer than N does not fit. N also can never change, because every reader already counts N bytes.

</ScrollStep>

<ScrollStep step={6}>

A delimiter breaks when a message holds the delimiter byte. In the animation, message 3 becomes a, then a newline, then c. The reader cuts at that newline, so it finds four messages, not three. The usual fix is to escape the byte. The sender writes each newline in the data as two other bytes, such as a backslash and an n, and the reader turns them back into a newline.

</ScrollStep>

### The real thing

HTTP, the protocol of the web, ends its header lines with a delimiter. A web server answers with a status line first, then header lines, one fact on each line, such as the date or the size of the body. Two bytes, CR and LF, end each line: that is how HTTP writes a newline. An empty line, one more CR LF, ends the header lines. Then the body follows, and Part 3 shows how HTTP marks the end of the body.

On <SlideLink session={1} page={17} />, the instructor typed a request to google.com by hand. Google answered with a 301 response, which says that the page moved. The bytes below are the end of its header lines, with `\r\n` for CR LF.

So the reader of a response scans for four bytes, CR LF CR LF: the end of the last header line, then the empty line.

<KeyIdea id="a-delimiter-marks-the-end" title="A delimiter marks the end, until the data holds it">

A delimiter is an agreed byte, or a short run of bytes, after each message. The reader checks the bytes until it finds it. HTTP ends its header lines with an empty line, so the reader scans for CR LF CR LF. If the data holds the delimiter, the reader ends the message too early, unless the sender escapes that byte.

</KeyIdea>

<ExamDepth>

- **Two rules or three?** <SlideLink session={1} page={39} /> lists three rules: fixed length, delimiter and length prefix. Later decks say "length or delimiter", for example <SlideLink session={2} page={41} />. Both hold, because a fixed length is a length that both sides agreed on ahead of time.
- **The cost of a fixed length.** The parse is trivial, and nothing is ambiguous. But every short message pays for pad, and N can never change.
- **The cost of a delimiter.** A delimiter is readable, and the sender needs no size up front. But the sender must escape the delimiter in the data. SMTP, the mail protocol, adds a dot to a body line that starts with a dot (<ModuleLink id="s02-m07-smtp-mime" />).
- **Are TCP/IP headers fixed length?** Notes from the class call them fixed size, and say that messages of variable length are more common today. In fact each header has a fixed part plus a length field. So even a "fixed" header carries a length.

<Beyond source="RFC 791 §3.1 (IPv4 IHL), RFC 9293 §3.1 (TCP Data Offset)" url="https://www.rfc-editor.org/rfc/rfc9293#section-3.1">

The IPv4 header and the TCP header each have a fixed part of 20 bytes. Options can follow. A length field in each header, IHL in IPv4 and Data Offset in TCP, gives the header size in 32-bit words.

</Beyond>

</ExamDepth>

<Segment title="A length before the bytes">

**In this part.** Part 2 gave two answers, and each one had a cost: pad and a size that never changes, or escapes. This part gives the answer that most modern protocols use: send the length before the bytes. Then you test all the rules in a sandbox and see which ones break.

<FramingSandbox slot="visual" title="Framing sandbox" messages={['hello', 'world']} rule="length" />

<Picture breaks="you would stop at a card that says 9,000 on a small parcel. A reader trusts the number. A wrong length makes it take the wrong bytes, and every later message breaks too.">

This time, your friend puts a small card on the string before each bracelet. The card says how many beads follow, such as 7. You read the card, then you slide off exactly 7 beads. The next thing on the string is the next card. Now a bracelet can hold beads of any color, even red, because you never look for an end bead.

In framing, the card is the length prefix, and its number is the byte count of the message. The beads after the card are the bytes of the message. The reader reads the length first, then takes exactly that many bytes. It never checks the data for an end marker, so the data can hold any byte.

</Picture>

### How it works

The sender counts the bytes of a message. It writes the count in a field of an agreed width, such as 1 byte, and then it writes the bytes. The reader reads the count first. Then it takes exactly that many bytes as one message, and the byte after them is the next count.

A read can still cut anywhere, as in Part 1. So the reader keeps the bytes of a message that is not complete yet, and it reads again until it has them all.

### The real thing

The same 301 response on <SlideLink session={1} page={17} /> holds the header line `Content-Length: 219`. It says that the body has exactly 219 bytes. After the empty line, the reader takes 219 bytes of body and stops. The body of that response is exactly 219 bytes.

HTTP writes that length as text, in a header line. A binary protocol writes the length as raw bytes. The view below shows each byte in hex, as two characters from 00 to FF, with its letter under it. The two bytes 00 05 give the length 5, high byte first, and then the 5 bytes of hello follow.

<ByteView
  caption="A 2-byte length, 5, then the 5 bytes of hello"
  messages={[
    {
      fields: [
        { hex: '00 05', kind: 'length', label: 'length: 5' },
        { text: 'hello', label: 'data' },
      ],
    },

One length byte can say at most 255, so it caps a message at 255 bytes. Two bytes can say up to 65,535. <SlideLink session={1} page={39} /> calls the length prefix binary-safe, and says that most modern protocols use it. Binary-safe means that the data can hold any byte at all.

<KeyIdea id="a-length-prefix-says-how-many" title="A length prefix says how many bytes follow">

The sender writes the size of each message before its bytes. The reader reads the size, then takes exactly that many bytes, with no search for an end. So the data can hold any byte. `Content-Length: 219` in an HTTP response is a length for the body.

</KeyIdea>

<ExamDepth>

- **Field width.** A 1-byte length caps a message at 255 bytes. 2 bytes cap it at 65,535 bytes, and 4 bytes at about 4 GB. A wider field costs more bytes on every message.
- **The cost of each rule.**

| Rule | Good | Cost |
|---|---|---|
| Fixed length | trivial parse | pad, and N can never change |
| Delimiter | readable, no size needed up front | escape the delimiter in the data |
| Length prefix | binary-safe, no scan | the sender must know the size first, and the field width caps it |
| Both | readable control lines, a safe binary payload | two parsers, two ways to fail, and request smuggling in the gap (<SlideLink session={2} page={36} />) |

- **Text or binary.** <SlideLink session={1} page={38} /> says that HTTP shows how far readable text can go, and that HTTP/2 is binary. A person can read text with telnet, tcpdump and logs, and the slide says that this is most of why HTTP won. Text is also verbose, ambiguous at the edges, and "slower to parse than it looks". Binary is compact and cheap to parse, with no whitespace rules and no arguments about upper and lower case. Its cost is tools: you need a hex dump to read it. Notes from the class add that binary suits places where speed and efficiency matter.
- **Redis uses both rules.** Homework 1 on <SlideLink session={1} page={47} /> calls Redis traffic text and length-prefixed. The Session 2 table on <SlideLink session={2} page={36} /> lists Redis under delimiter. Both hold. A Redis command sends each argument as a length, CR LF, the bytes, then CR LF. Some replies, such as `+OK`, end with CR LF and carry no length.

<Beyond source="Redis serialization protocol specification, sections Bulk strings, Arrays and Sending commands" url="https://redis.io/docs/latest/develop/reference/protocol-spec/">

The command `LLEN mylist` crosses the wire as `*2\r\n`, then `$4\r\nLLEN\r\n`, then `$6\r\nmylist\r\n`, with no gaps. `*2` says that two elements follow. In each element, `$N` gives the byte count of the data after it, and CR LF ends each line. The view frames the three messages of Part 2 in the same way.
