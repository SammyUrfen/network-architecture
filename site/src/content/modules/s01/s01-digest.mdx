Class 1 builds a working network server out of nothing, then breaks it on purpose. This page is the fast read of that class: about 18 minutes, plus 8 minutes of questions.

The bugs that look like magic in Express, Flask or nginx all live at this layer. A server that hangs and answers nobody. A server that dies with no error message. A message that arrives cut in half. Class 1 gives each one a plain cause.

**The path through this digest.** Part 1 builds a TCP server from seven requests to the operating system, and gives it a door number. Part 2 meets the one write that kills a server in silence, and the client behind it. Part 3 opens two translations hidden in a twenty-line client, then the two ways to serve many clients. Part 4 reads the real bytes, and meets the wrapper that hides them. Part 5 designs bytes of your own.

Each part ends with three questions, and links to the full lesson. After the parts come the numbers, an exit quiz and the cards.

<Segment title="Seven calls and one door number">

**In this part.** Class 1 starts with a server of about twenty lines of C. You learn the seven requests that it makes to the operating system, and the two settings that decide what a client sees before your own code runs at all.

A program never touches the network itself. It asks the kernel, and the kernel does the work. A TCP server asks seven times, always in the same order: `socket()`, `bind()`, `listen()`, `accept()`, `read()`, `write()`, `close()`. The class echo server reads one time, writes the same bytes back, closes, and loops to the next client. The persistent version of it loops on one client until `read()` returns 0, which is how the kernel says that the client closed its side.

Think of a shop in a mall. The shopkeeper cannot build walls, so the mall office gives a shop, a number on the door and a guard who lines customers up. The shopkeeper calls "next, please", hears a word, says it back, and calls the next customer. Where this breaks: the guard only lines customers up, but the kernel finishes the whole handshake before your program hears about the client.

<KeyIdea id="seven-calls-are-the-whole-server" title="Seven calls are the whole server">

Every TCP server makes the same seven requests to the kernel: socket, bind, listen, accept, read, write, close. Express, Flask and the Go `net/http` package wrap those calls under their own names. They do not replace them. Run your framework under `strace` and you can find the `accept()` inside it.

</KeyIdea>

Now the door number. `bind()` claims a port, and one rule comes with the number: only root may claim a port below 1024, and any user may claim 1024 and up. <SlideLink session={1} page={8} /> lists the low ports 80 for HTTP, 443 for HTTPS, 25 for SMTP, 21 for FTP and 110 for POP. The rule has a security cost. A server on port 80 runs as root, so one bug in its request parser hands an attacker the whole machine. Real deployments bind 8080 as a normal user, behind a front proxy that owns 80 and 443. The class server also binds `INADDR_ANY`, every interface including your LAN. Bind `127.0.0.1` for this machine only.

<Myth myth="Nothing can use a port below 1024 without root, ever.">

The 1024 line says **who may break the rule**, not that nobody can. Root can bind a low port, and any user can bind 1024 and up. The rule is a privilege, not a wall.

</Myth>

<Beyond source="capabilities(7) and ip-sysctl, Linux documentation" url="https://man7.org/linux/man-pages/man7/capabilities.7.html">

Linux lifts the line without full root in two ways. The capability `CAP_NET_BIND_SERVICE` gives one program the right to bind a low port, and no other root power. The setting `net.ipv4.ip_unprivileged_port_start` moves the line itself.

</Beyond>

The second setting is the queue. Skip `bind()` and the client gets "Connection refused" at once: it sends a SYN, the packet that asks to open a connection, and the kernel answers with an RST, a flat refusal. Call `bind()` and `listen()` but never `accept()`, and the opposite happens. The kernel finishes the handshake anyway, the connection waits in a queue, and the client hangs with no reply. The first failure is fast and loud. The second is silent and slow, and it looks like an overloaded server. The second argument of `listen()` sizes that queue, and Linux holds its own ceiling in `net.core.somaxconn`. When `accept()` returns, the connection already exists, because the client already waited in line. The backlog is the depth of that queue, not a limit on the clients you can serve.

One more trap sits at restart. A connection that your server closed first holds its port in TIME_WAIT for about a minute, so a quick restart fails with "Address already in use". Set `SO_REUSEADDR` before `bind()` on every start, and the restart works.

<Myth myth="A full accept queue refuses the next client.">

A full queue is **not portable**. Some systems refuse at once, and some leave the client on an endless "Trying...". Never build logic on the behavior that you saw on your own machine.

</Myth>

<Beyond source="tcp(7) and the Linux kernel function tcp_conn_request" url="https://man7.org/linux/man-pages/man7/tcp.7.html">

Linux drops the new SYN in silence. The client sends it again with longer gaps, and `connect()` fails after about two minutes.

</Beyond>

<Remember>

- The seven calls, in order: socket, bind, listen, accept, read, write, close.
- read() returns 0 when the peer closed its side.
- No bind(): refused at once. No accept(): the client hangs with no reply.
- The second argument of listen() sizes the accept queue, not the client count.
- A port below 1024 needs root. Bind 8080 behind a front proxy.
- Set SO_REUSEADDR before bind(), or a quick restart fails.

</Remember>

<Segment title="The write that kills the server">

**In this part.** Part 1 left the server alive and looping. Now one client leaves in the middle of an answer, and the server is gone with no error message. You learn the signal behind that, and then you meet the client program itself, which is the same seven calls with three of them removed.

Think of a game of catch over a low wall. Your friend throws the ball over, then runs off without a word. You count to ten and throw it back two times. A teacher sees the second throw to nobody and sends you inside. You are the server, your friend is the client, and each throw is one `write()`. Where this breaks: nobody stays behind the wall, but the kernel of the client stays and still answers.

A write to a socket that the peer already closed kills your process by default, with no error message. The killer is SIGPIPE, signal 13. The numbers you meet most: 2 is SIGINT from Control-C, 9 is SIGKILL, 13 is SIGPIPE and 15 is SIGTERM. SIGTERM is the polite kill, because a program can catch it and clean up. No program can catch SIGKILL. A shell reports 128 plus the signal number, so the demo server leaves the exit status 141.

The demo makes the death certain. The server reads one time, sleeps one second, then writes two times, and the second write never runs. The client sets `SO_LINGER` to `{1, 0}`, which makes `close()` send RST in place of FIN. A normal close sends FIN and leaves the closing side in TIME_WAIT. A linger-zero close sends RST, drops unsent data and skips TIME_WAIT. It is fast and lossy, so keep it in a demo.

<KeyIdea id="a-dead-peer-kills-the-writer" title="A dead peer kills the program that writes to it">

Writing to a connection that the other side already ended raises SIGPIPE, and the default action of SIGPIPE ends your process with no message. A server must opt out, with `signal(SIGPIPE, SIG_IGN)` or the `MSG_NOSIGNAL` flag, and then check the result of every write.

</KeyIdea>

<Beyond source="the Linux kernel function sk_stream_error, and a verified run on Linux 7.1 over loopback">

The code comment of the class demo puts SIGPIPE on the first write. On Linux the first write after a reset returns ECONNRESET, and the second one gets EPIPE and the signal. A traced run of the demo shows that order.

</Beyond>

Now turn the connection around. The client is the same list with three calls gone: `socket()`, `connect()`, `write()`, `close()`. It has no bind, no listen and no accept. `connect()` starts the TCP handshake. Clients do not bind, because the kernel picks the client port at `connect()` time, from the ephemeral range 32768 to 60999 on Linux. A server binds a known port for the opposite reason: clients need a fixed address to aim at. After a close, the side that closed first holds the port in TIME_WAIT for about 60 seconds on Linux, which RFC 9293 states as 2 MSL. A busy client runs out of ports.

You do not need to write a client to try any of this. Class 1 makes that point first: you already have clients. `telnet` opens any TCP port, `nc` connects to one and `nc -l` listens on one, and `openssl s_client` does the TLS handshake for an encrypted service. If a protocol is text, your keyboard is already a working client for it.

<Remember>

- SIGPIPE is signal 13, and a shell shows 128 + 13 = 141.
- On Linux the first write after a reset gets ECONNRESET, the next one SIGPIPE.
- SIGKILL cannot be caught. SIGTERM is the polite kill.
- SO_LINGER {1, 0} makes close() send RST: unsent data dropped, no TIME_WAIT.
- A client is socket, connect, write, close. The kernel picks its port at connect().
- Linux holds TIME_WAIT for 60 s, on the side that closed first.

</Remember>

<Segment title="Two translations and many clients">

**In this part.** Two steps hide inside the twenty-line client before its first byte leaves: a number swap and a name lookup. The name lookup can block for seconds, and that leads straight to the last question of the class demo. How does one program serve more than one client at a time?

Think of one tutor in a room of students. The tutor helps one student, and the rest wait at the door. One fix clones the tutor, and each clone needs a desk. The other puts a bell on every desk, and one tutor walks only to a desk that rings. The clone is `fork()`, and the bell is `epoll`. Where this breaks: a real clone costs more than a fork child, which shares the memory of its parent.

Port 2026 is 0x07EA. Any normal x86 or ARM laptop is little-endian and stores that as `EA 07`, low byte first. Network byte order is the opposite, so the wire carries `07 EA`. The call `htons()` makes that swap: "host to network, short". `htonl()` does four bytes, and `ntohs()` and `ntohl()` convert back. Forget the swap on x86 and your server binds port 59911 in silence, and every client that aims at 2026 gets refused.

The second translation is the name. A lookup reads `/etc/hosts` first, before any network traffic, so a stale line there beats the whole internet. For any other name it sends one UDP datagram to your resolver, which recurses through the root, the TLD and the authoritative servers. The answer stays in a cache for its TTL, so the lookup is fast when warm and slow when cold. Use `getaddrinfo()` in real code: `gethostbyname()` is IPv4 only and not thread-safe.

<Myth myth="gethostbyname() is a quick local lookup, like reading a variable.">

It is **a whole protocol behind one plain-looking call**. It can read files, send UDP, wait for a recursion across the internet, and block your program for seconds. The call gives you no timeout that you control. One slow lookup inside a single-process server stalls every client of that server.

</Myth>

That last sentence is the bridge. A layer is one job in a stack, and each job hands its work to the job below it. Twenty lines of C already touch three. The echo text is layer 7. TCP and the port are layer 4. The IP address is layer 3.

The echo server serves one client at a time, and class 1 gives two ways past that. The first is `fork()` for each connection. It is simple, the operating system does the scheduling, and a crash stays inside one child. `fork()` returns twice: 0 in the child, the child process ID in the parent, and -1 on failure. The parent closes its own copy of the client descriptor and goes back to `accept()`. Skip that close and the client never sees the end of the data. The cost is one process for each client: fine for hundreds, hopeless at ten thousand.

The second way asks the kernel which sockets are ready. `select()` is portable and O(n): you rebuild the set on each call, and the kernel walks all of it. It also cannot watch a descriptor number above FD_SETSIZE, 1024. `epoll` is Linux only and O(ready): register interest one time, and get back only the descriptors that changed. nginx and Node are built this way. The event loop is harder to write, and one slow handler blocks every client. Both designs still ship today.

<KeyIdea id="one-blocked-call-stops-everyone" title="In one process, one blocked call stops everyone">

A single process that waits inside `read()`, or inside a name lookup, serves nobody else while it waits. `fork()` buys isolation with one process for each client. An event loop with `select` or `epoll` keeps one process and asks the kernel which sockets are ready. It pays for that with one slow handler, which blocks every client.

</KeyIdea>

<SlideLink session={1} page={29} /> says that select and epoll need "no context switching" and "no per-client memory". Read both as no process and no stack for each client. One process still switches between sockets, and each connection still holds a buffer and some state. The same shortage shows up on the client side. Chrome opened at most 6 connections to one host, and requests 7 to 10 waited in a queue. `ulimit -n` is your ceiling on open descriptors, often 1024, and a socket counts as one. A connection pool answers all of it: open a connection one time and reuse it, so later requests skip the TCP and TLS handshakes.

<Myth myth="The six-connection cap is an old browser quirk.">

It is **the client side of the same resource problem**. Descriptors, memory and handshakes cost something on both ends, so the browser rations them. No HTTP standard sets the number.

</Myth>

<Beyond source="Chromium net/socket/client_socket_pool_manager.cc, and RFC 9112 section 9.4">

The class calls six the old cap. Chromium still allows six sockets for each host group in its normal pool, and RFC 9112 sets no fixed number at all.

</Beyond>

<Remember>

- Network byte order is big-endian. 2026 is 0x07EA, and the wire carries 07 EA.
- Forget htons() on x86 and the kernel binds 59911 in silence.
- A name lookup reads /etc/hosts first, then sends one UDP query to the resolver.
- fork() returns 0 in the child, the child PID in the parent, -1 on failure.
- select is O(watched) and stops at 1024. epoll is O(ready) and Linux only.
- A pool pays the TCP and TLS handshakes one time, then reuses the connection.

</Remember>

<Segment title="See the bytes until a wrapper hides them">

**In this part.** The bytes of a text protocol are readable, and two tools show them to you. Then TLS wraps them and they are gone. You also learn the three encodings that let you read bytes that were never text.

<ByteView

Think of a postcard in the mail. Every post office on the way can read it, and so can anybody who picks it up. TLS is an envelope around that postcard, and any card fits inside one. Where this breaks: the envelope still shows the address, the size and the day of posting.

An HTTP client is the plain client of Part 2 with a request string added: connect to port 80, write the text, and read until the server closes. That last rule is the one the class gives, and it has a cost: HTTP/1.1 keeps the connection open by default, so a `Content-Length` header is how a client finds the end of the body. The text rules are strict. Every line ends in CR LF, and the blank line after the headers is mandatory. Miss it and the server waits for headers that never come. `curl` is the teaching tool that class 1 recommends for HTTP: `curl -i` shows the reply headers, and `curl -vv` adds the connection and TLS detail. For the packets themselves, `tcpdump` has four flags worth knowing:

- `-w` writes a capture of one port to a file.
- `-r` reads that file back.
- `-A` shows the bytes as ASCII.
- `-X` shows hex beside the ASCII.

Then TLS arrives and the readable bytes stop. Two sides use asymmetric cryptography to agree on a shared secret, then switch to much faster symmetric cryptography for the data. A certificate binds a public key to an identity, and the chain of certificate authorities behind it is why you trust it. A certificate also expires, sometimes at three in the morning.

<Myth myth="SSL secures HTTP.">

**SSL secures TCP**, not HTTP. It sits under the application protocol, so the same machinery protects SMTP and database connections as well. That also tells you what a sniffer still sees: the IP addresses, the ports and the sizes stay in the clear, because TLS rides on TCP and does not hide it.

</Myth>

<KeyIdea id="tls-wraps-tcp-not-http" title="TLS wraps TCP, not HTTP">

TLS is a wrapper around a reliable byte stream. Any protocol on TCP can use it, which is why one library covers HTTPS, mail and databases. It hides the content of the stream. It does not hide who is talking to whom, on which port, or how much.

</KeyIdea>

Not every byte you meet is text. Three encodings cover the rest of class 1, and each is a fixed rule between values and bytes, with nothing secret about it. BCD packs one decimal digit into four bits, so one byte holds two digits. The five digits 98765 become the three bytes `98 76 5F`, and the last nibble F is padding for the odd digit count. A hex dump of BCD shows the decimal digits unchanged, so you read them by eye. Hex is for reading: two characters for each byte. base64 is for transport. It carries any bytes through a channel that accepts text only, such as Basic authentication, a JWT or an email attachment. Its cost is 33% more bytes, because every 3 bytes become 4 characters.

<Remember>

- Every HTTP line ends in CR LF, and the empty line after the headers is mandatory.
- curl -i shows the reply headers. tcpdump -X shows hex beside the ASCII.
- TLS sits under the application protocol, on TCP. SMTP and databases use it too.
- TLS agrees a secret with asymmetric crypto, then moves data with symmetric crypto.
- BCD holds one digit in four bits: 98765 packs to 98 76 5F, with F as the pad.
- base64 costs 33% more bytes and hides nothing.

</Remember>

Think of a friend who sends you two bead bracelets in one thin tube, every bead on one long string. You take the beads off a handful at a time, and one handful can hold the end of the first bracelet and the start of the second. Nothing on the string shows where the first one stopped. A bead is a byte, a bracelet is a message, and each handful is one `read()`. Where this breaks: a real string can snap, but TCP never loses a byte.

Start with text against binary. Text won the web, because a person can telnet in and read it, then read it again in a log. The cost of text is that it is verbose, ambiguous at the edges and slow to parse. Binary is compact, unambiguous and cheap to parse, and it needs tools, which is why hex and base64 fluency matters. Protocols are going binary again: HTTP/1.1 is text and HTTP/2 is binary.

Then the central question. TCP gives a byte stream, not messages, so framing is the most important decision in any protocol. <SlideLink session={1} page={39} /> gives three answers. A fixed length is trivial and unambiguous, but it wastes padding and N can never change. A delimiter, like the blank line in HTTP, is simple until the delimiter turns up inside the data. A length prefix, like `Content-Length: 219`, is binary-safe, and most modern protocols use it. Later decks in this course say only "length or delimiter". Both statements hold, because a fixed length is a length that both sides agreed on ahead of time, in the specification instead of in each message.

<KeyIdea id="every-protocol-must-say-where-a-message-ends" title="Every protocol must say where a message ends">

TCP keeps every byte and its order, and it keeps no mark where one `write()` stopped. So the protocol adds the mark. Either the reader knows the count ahead of time or reads it from a prefix, or it scans for a delimiter and pays the escaping cost.

</KeyIdea>

Put a type and a length before each value and you get TLV, which the class calls "ASN.1 you can write on a napkin". The payoff is forward compatibility. A parser that meets a type it never saw reads the length and jumps exactly that many bytes, so a version 1 parser survives a version 2 sender. TLS extensions, ISO 8583 and protobuf all use the idea. ASN.1 is the grown-up form: write the grammar one time, and a tool generates the encoder and the decoder. Its DER rules give the bytes. A DER INTEGER is the tag `0x02`, a length and the value. A DER SEQUENCE is the tag `0x30`, a length and its child records.

The class ends with RPC, which is framing plus a function name. You marshal the name and the arguments, frame them and send them. The two steps have names: marshalling and demarshalling. But the network is not a function call. A call can fail halfway. It can time out when the work may or may not have run. It can be retried and run twice. gRPC is the modern shape of the idea: protobuf underneath, faster than JSON and easier to understand than ASN.1. It is schema first, so one `.proto` file generates client and server code in any language. protobuf puts tag, length and value on the wire, so new fields do not break old clients. It runs on HTTP/2, which is binary and carries many streams over one connection. The price is debuggability: plain `curl` cannot read a gRPC call.

<Remember>

- TCP is a byte stream with no message edges. Framing is the first decision.
- Fixed length wastes padding. A delimiter needs escaping. A length prefix is binary-safe.
- A fixed length is a length agreed ahead of time, so the rule is length or delimiter.
- TLV lets an old parser skip an unknown type by jumping over its length.
- DER INTEGER is tag 02, and it adds a leading 00 when the top bit is 1. SEQUENCE is tag 30.
- A timeout tells you nothing about the work. Retry only what is idempotent.

</Remember>
