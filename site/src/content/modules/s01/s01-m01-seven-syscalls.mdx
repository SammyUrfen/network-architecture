You open a web page, and your browser talks to a program on another computer. That program is a server. It waits for other programs to connect, and then it answers them. So how does a server really talk over the network? This lesson answers that question.

The answer is short. A byte is the smallest piece of data that a program sends, such as one letter. A server makes seven requests to the kernel, the core of the operating system, in the same order every time. The first class used an echo server of 20 lines, a tiny server that sends back what it gets. It makes the seven requests. Express, Flask and Go's net/http, three toolkits that people use to build web servers, make the same seven. When a server hangs, dies with no message, or cuts a message in half, the cause is often in these calls.

Much of the course stands on them: many clients at once, the web server nginx, and HTTP, the rules of the web. So do the two graded builds that the course announces: a calculator assignment, and a project that sends HTTP as raw bytes instead of text.

This is the first lesson, so you need nothing before it. The servers here use TCP, the set of rules that carries the bytes of most of the internet, in order. The top of the page names one thread, Framing. A thread is a big idea that comes back in many lessons. This one starts in Part 4 and continues in the lesson <ModuleLink id="s01-m08-framing" />.

**The path through this lesson.** Part 1 shows why a program must ask the kernel for all network work, and it names the seven requests. Part 2 follows the first three calls, which set up the server before any client comes. Part 3 follows the other four calls, which serve one client, in the echo server of the first class. Part 4 shows why one read is not a whole conversation, and how the second server of the class fixes that.

### How it works

A program cannot send one byte over the network by itself. Only the kernel uses the network card, so a program asks the kernel for each step. A TCP server asks for seven steps, always in this order. Scroll through them, and the picture next to the text follows.

<ScrollStep step={1}>

**1.** `socket()` asks: make me a socket, one end of a connection.

</ScrollStep>

<ScrollStep step={2}>

**2.** `bind()` asks: give my socket a port, such as 2026, so that clients can find it.

</ScrollStep>

<ScrollStep step={3}>

**3.** `listen()` asks: take clients on that port for me, and keep them in a line.

</ScrollStep>

<ScrollStep step={4}>

**4.** `accept()` asks: give me the next client from the line.

</ScrollStep>

<ScrollStep step={5}>

**5.** `read()` asks: give me the bytes that this client sent.

</ScrollStep>

<ScrollStep step={6}>

**6.** `write()` asks: send these bytes to this client.

</ScrollStep>

<ScrollStep step={7}>

**7.** `close()` asks: end the connection with this client. The server then goes back to step 4 for the next client.

</ScrollStep>

<ScrollStep step={8}>

A client makes a shorter list. It calls `socket()` too, then `connect()`, which asks the kernel to connect to a server at its address and port. Then it calls `write()` to send, `read()` if it wants an answer, and `close()`. The lesson <ModuleLink id="s01-m04-clients" /> shows the client in full.

</ScrollStep>

<KeyIdea id="seven-calls" title="A TCP server is seven system calls">

`socket`, `bind`, `listen`, `accept`, `read`, `write`, `close`, in that order. The program only asks, and the kernel does the network work. Express, Flask and Go's net/http make the same seven calls for you.

</KeyIdea>

Back in the mall, the shopkeeper asks the office for a shop. The office hands over a key with a tag on it: key 3. ### How it works

<ScrollStep step={1}>

`socket()` asks the kernel for a new socket. The kernel returns a small number, the file descriptor, and the program uses that number in every later call. The first socket of the class server gets 3.

</ScrollStep>

<ScrollStep step={2}>

`bind()` gives socket 3 a port. A port lets one computer run many servers, because each server takes a different port. The class server takes port 2026. `bind()` returns 0, which means that the call worked.

</ScrollStep>

<ScrollStep step={3}>

`listen()` turns socket 3 into a listening socket, with a line for clients that wait. From now on, the kernel takes clients on port 2026 for the program.

</ScrollStep>

<ScrollStep step={4}>

Then a client calls `connect()`. The kernel of the client and the kernel of the server trade a few short messages to agree that the connection exists. That exchange is the TCP **handshake**. No code of the server program runs during it.

</ScrollStep>

<ScrollStep step={5}>

The kernel puts the finished connection in the line. The program still did not call `accept()`, so it does not know about the client yet. Part 3 starts at this point.

</ScrollStep>

<KeyIdea id="kernel-answers-before-accept" title="The kernel answers clients before accept()">

After `listen()`, the kernel finishes the handshake with each client by itself and keeps the connection in a line. So when `accept()` gives a client to the program, the connection already exists.

</KeyIdea>

<ExamDepth>

- **`accept()` does not do the handshake.** A common wrong idea is that `accept()` runs it. The kernel ran the handshake earlier, while the client waited in the line. `accept()` only hands the finished connection to the program.

### How it works

`accept()` takes the first connection from the line. It returns a new file descriptor, 4 in the class server, that names this one client. Socket 3 stays open, so other clients can join the line while the server talks to this one.

`read()` asks the kernel for the bytes that this client sent. The program gives it the number 4 and room for up to 4096 bytes. If no bytes wait, `read()` waits. When some bytes arrive, it returns at once with the bytes that wait, and its result is how many bytes it got.

`write()` hands bytes to the kernel to send to the client, and its result is how many bytes the kernel took. The echo server passes the same bytes and the same count that `read()` gave, so the client sees its own text come back.

`close()` ends the connection with this client and frees the number 4. The server goes back to `accept()`, and the next client gets the number 4 again.

<KeyIdea id="set-up-once-then-loop" title="Set up once, then loop for each client">

`socket`, `bind` and `listen` run one time. `accept`, `read`, `write` and `close` run again for every client, and `accept()` gives each client its own file descriptor.

</KeyIdea>

Try it in the theater next to this text. Press "Next call" to step the server, and use the client buttons to connect, send lines and quit. Send one line and step the server to `close()`. Then send the second line, and look at what comes back.

### The real thing

The rest of `01_echo_server.c` is one loop <SlideLink session={1} page={6} />. Line 15 calls `accept()`, line 17 calls `read()` one time, line 18 writes the same bytes back, and line 19 calls `close()`. The class ran it with two commands <SlideLink session={1} page={7} />. The command `gcc` turns the C file, a file of code in the programming language C, into a program. The tool `nc` connects to port 2026, sends what you type, and prints what comes back.

On Linux, an operating system like Windows, the tool `strace` prints each system call of a program, one on each line. A line gives the name of the call, its arguments in brackets, and its result after the equals sign. In a string, `\n` is the newline byte at the end of a line. Here the first server served one client that sent `one` and a newline. The run used Linux 7.1.8 over loopback, which means with the client and the server on the same computer (2026-09-14):

```
accept(3, NULL, NULL)                   = 4
read(4, "one\n", 4096)                  = 4
write(4, "one\n", 4)                    = 4
close(4)                                = 0
```

`accept()` on socket 3 returns 4. Its two `NULL` arguments mean that the server does not ask who the client is. `read()` on 4 gets 4 bytes, the three letters and the newline, and `write()` sends the same 4 bytes back. `close()` returns 0, which means that it worked.

<ExamDepth>

- **A client sends 10,000 bytes at once.** One `read()` takes at most 4,096 bytes, the size of the room that the server gives it. The server writes those bytes back and closes while more bytes still wait. A run on Linux over loopback gave 4,096 bytes back to the client, then the error "Connection reset by peer" (2026-09-14). The peer is the other end of the connection, and a reset is a message that ends the connection at once.
- **Why no error checks?** The class code checks nothing, to stay short. A real server checks each result, because any call can fail.

<Beyond source="RFC 9293 §3.6.1, Half-Closed Connections" url="https://www.rfc-editor.org/rfc/rfc9293#section-3.6.1">

Received bytes can still wait unread when a program closes a connection. The TCP standard says that TCP should then send a reset, to show that data was lost. Linux does that, so the client sees a reset and not a normal end.

</Beyond>

</ExamDepth>

### How it works

The second server of the class, `02_echo_server_persistent.c`, puts `read()` and `write()` in a loop. It reads, writes the same bytes back, and reads again, for as long as the client stays connected.

When the client closes its side, the kernel tells the server with a special result: `read()` returns 0. That result means end of file, the sign that no more bytes will come. The loop stops at 0, and the server calls `close()`.

A read also takes every byte that waits, up to the room that it has. If the client sends two lines very fast, both lines can wait before the server reads, and one `read()` returns both. The kernel keeps bytes that arrive early, until a read takes them.

<KeyIdea id="loop-until-read-returns-0" title="Loop until read() returns 0">

One `read()` gets only the bytes that wait at that moment. A server that talks with a client calls `read()` in a loop. A result of 0 means that the client closed its side, so the server calls `close()`.

</KeyIdea>

In the theater, pick the second server. Send two lines before you step the server to `read()`, and count the lines that one read returns. Then quit the client and step the server until it calls `close()`.

### The real thing

The slide of the second server has the title "One read() is not a conversation" <SlideLink session={1} page={10} />. Line 18 of `02_echo_server_persistent.c` holds the loop: it calls `read()` again for as long as the result is more than 0. Here is `strace` of that server with one client (Linux 7.1.8, loopback, 2026-09-14). The client sends `one`, then `two` half a second later, then quits:

```
accept(3, NULL, NULL)                   = 4
read(4, "one\n", 4096)                  = 4
write(4, "one\n", 4)                    = 4
read(4, "two\n", 4096)                  = 4
write(4, "two\n", 4)                    = 4
read(4, "", 4096)                       = 0
close(4)                                = 0
```

With the same client, the first server gave back only `one`. The half second matters, because the only read of the first server returns before `two` arrives.

Now you know how a server gets bytes. The next big question is where one message ends, when one read can hold part of a message or two messages. That is the subject of the lesson <ModuleLink id="s01-m08-framing" />.

<ExamDepth>

- **A read loop is not a message loop.** The loop runs one time for each read, not one time for each line. The echo server needs no more, because it only copies bytes back. A chat server or a calculator must find where each message ends, and one read can end in the middle of a message.
- **Why does 0 mean "done" and not "nothing yet"?** A `read()` with no bytes waits. It returns 0 only when no more bytes can ever come, because the client closed its side.

</ExamDepth>
