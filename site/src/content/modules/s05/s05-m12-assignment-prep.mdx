### How it works

These are concepts, not code.

1. Collect bytes until the head ends at an empty line.
2. Parse the request line and the headers from those bytes only.

Use the finder below. Step through the reads, and watch where each read ends. Then change the sizes, and try to make every read end exactly where a request ends.

<BoundaryFinder slot="visual" />

### The real thing

Slide 3 names the hard part of the assignment: where does this request end, and where does the next one begin? The arithmetic is not the point.

<Beyond source="recv(2), Linux man page" url="https://man7.org/linux/man-pages/man2/recv.2.html">

The man page says that the receive calls "return any data available, up to the requested amount". So `recv(4096)` gives the bytes that wait, from 1 byte up to 4096. It does not wait for one whole request.

</Beyond>

<ExamDepth>

**Why framing is the whole task.** An HTTP/1.0 server closed the connection after one response. No request came after the first one, and the close marked the end of the response for free. On a kept connection, the next request follows on the same bytes, and nobody closes. Only your parser can mark where one request ends (S05-C09).

**What if a read ends inside the empty line?** Bytes 0 to 60 of the finder stream end in CR LF CR, with no last LF. The head is not complete yet. Keep the bytes and read again. In the finder, type 61 as the size to see it.

</ExamDepth>

### How it works

The steps go on from part 1.

3. If the request declares a body, collect exactly that many more bytes. Keep any extra bytes for the next request.
4. Pick a status, and send a response with its own Content-Length.
5. Go back to step 1 on the same socket. Stop when the client closes or asks to close, or when a timeout fires.

The stepper uses the stream and the reads of the finder: 30 bytes, then 50, then 34.

### The real thing

Slide 3 says it plainly: consume exactly Content-Length bytes, "and not one more". Byte n+1 belongs to the next request.

<Beyond source="RFC 9112 §6.3" url="https://www.rfc-editor.org/rfc/rfc9112#section-6.3">

A valid Content-Length with no Transfer-Encoding gives the body length in bytes. A request with neither header has a body length of zero. That is why request 2 ends at its empty line.

</Beyond>

<ExamDepth>

**The timeout trade-off.** A short idle timeout frees server memory, but it drops a slow client. A long timeout keeps idle sockets open. The lab server sends `Keep-Alive: timeout=15, max=100` on the wire (our capture, scratch copy, loopback, 2026-09-13). Pick your own number, and be ready to defend it (S05-C10).

**Pipelining.** If six requests arrive in one read, answer them in order. A response carries no request number, so the client matches each response to a request by its position. RFC 9112 §9.3.2 requires the same order.

**Why a response needs its own length.** The client reads a kept connection too. Without a length on the response, a Content-Length or chunked encoding, the client cannot find where the response ends.

</ExamDepth>

### How it works

Pick the status by what is wrong. Do not pick it by where your code found the problem.

| What is wrong | Status | Example from slide 3 |
|---|---|---|
| the input | 400 Bad Request | `GET /div?a=1&b=0`, `GET /add?a=x&b=3`, no Host header |
| the resource | 404 Not Found | `GET /pow?a=2&b=8` |
| the method on this path | 405 Method Not Allowed | `POST /add` |

The marker sends the six requests of row 10 on one socket and then checks that the socket is still open. In the words of slide 3, a socket that dies early means you wrote "a 1996 server" (S05-C08, S05-C11).

<Beyond source="RFC 9110 §15.5.6, RFC 9112 §3.2" url="https://www.rfc-editor.org/rfc/rfc9110#section-15.5.6">

A 405 means that the server knows the method, but the target resource does not support it. The server must send an Allow header with the methods that the resource supports. RFC 9112 §3.2 also requires a 400 for an HTTP/1.1 request with no Host header.

</Beyond>

<ExamDepth>

<Beyond source="RFC 9110 §15.6.1, §15.6.2" url="https://www.rfc-editor.org/rfc/rfc9110#section-15.6.1">

**Why not 500 for a division by zero?** RFC 9110 §15.6.1 keeps 500 for an unexpected condition inside the server. A division by zero comes from the client input, and the server can see it before it divides. So the answer is 400.

**Why not 501 for POST?** RFC 9110 §15.6.2 uses 501 when the server does not recognize the method for any resource. Your server knows POST as a method. Only this path refuses it, so the answer is 405.

</Beyond>

**Errors on a kept connection.** The marking run holds three errors: a 400, a 404 and a 405. The socket must stay open through all of them. Slide 3 does not say what must happen after the no-Host 400 or the a=x 400. Test those cases on separate connections, and ask the instructor.

</ExamDepth>

## Build kit: test plan and hints

The Session 5 deck announces the assignment and says that it is due before Session 7 (about Friday 2026-09-25). The course has not formally set it yet. When the real task text comes, check it against the checklist in part 3.

### Local test plan

Run these against your own server, on a spare port.

1. Open one socket with a short client of your own. Send the six requests of the marking run in its order: add, sub, mul, div by zero, pow, POST /add. Check each result, and then check that the socket still works.
2. Test rows 4, 6 and 9 of the checklist (div 9/3, a=x, no Host) on separate connections.
3. Send one request in two writes, 1 s apart, split inside a header line. Expect one correct response.
4. Send two requests in one write. Expect two responses, in order.
5. Send a POST with `Content-Length: 5`, then 5 body bytes and a GET, all in one write. Expect two responses.
6. Send `Connection: close`. Expect one response, then end of file.
7. Stay idle past your timeout. Expect the server to close the connection.
8. Send a pipelined pair with the instructor tool: `python3 tools/talk.py PORT --keep-open --req "GET /add?a=2&b=3 HTTP/1.1" "Host: localhost" "" "GET /mul?a=6&b=7 HTTP/1.1" "Host: localhost" ""`
