## 2. The session in one paragraph

A server that talks to one client is easy. The hard question is how one box holds ten thousand clients at the same time. This session compares three answers: a process per client, a thread per client, and one loop that watches every socket. It shows what each client costs: a descriptor, a stack, a buffer, and trips into the kernel. It then shows how a web server runs your code: CGI starts a new program per request, FastCGI and servlets keep the program alive. It ends with the four walls every server hits, the law that ties concurrency to latency, and the proof that Apache, HAProxy, Varnish and nginx all arrived at the same shape. A working engineer cares because every capacity plan, every out-of-memory page at 3 a.m., and every "why is this loop stuck" bug comes back to these costs.

### s03-m01-threads-and-fork

- **Title:** Fork or thread: what one client costs.
- **Minutes:** 20.
- **Big idea:** A process or a thread per client works, but every client costs memory and kernel bookkeeping before it does any work.
- **Covers:** S03-C02, S03-C03, S03-C04, S03-C05, S03-C06, S03-C07, S03-C08, S03-C09, S03-C10, S03-C11, S03-C13, S03-C14, S03-C15, S03-C16, S03-C17, S03-C18, S03-C19, S03-C20, S03-C21, S03-C22, S03-C23, S03-C24, S03-C25, S03-C26, S03-C27, S03-C162, S03-C168.
- **Prereqs:** s01-m01-seven-syscalls, s01-m06-many-clients.
- **Threads:** T-setup-off-path.

**Pretest.**
1. A server makes 10,000 threads with the default Linux stack. About how much address space do the stacks take? *Answer: about 80 GB (78.1 GiB).*
2. Does that server use 80 GB of RAM? *Answer: no. The stack reserves address space. RAM grows only with the pages a thread touches.*
3. After fork, does the child get a full copy of the parent memory at once? *Answer: no. Linux copies the page tables and shares the pages until one side writes.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| A restaurant builds a new copy of its kitchen for each guest. | fork per client: a new process with its own address space. |
| A restaurant hires one waiter per table. Each waiter gets a big locker, even when idle. | thread per client: each thread reserves a stack. |
| One waiter walks the room and stops only at tables with a raised hand. | one loop with select or epoll. |

Where this breaks: a copied kitchen costs its full size at once. fork shares the pages until a write. And the locker is mostly empty space on a map (virtual memory), not floor space (RAM).

**Rung 2, how it works.**
1. The server calls `accept` and gets a new client socket.
2. Fork model: it calls `fork`. The kernel copies the page tables, the descriptor table and the task entry. The child serves the client and exits.
3. The parent closes its copy of the client socket and goes back to `accept`.
4. A dead child stays a zombie until the parent calls `waitpid`.
5. Thread model: it calls `pthread_create`. The kernel maps an 8 MiB stack and adds one scheduler entry. The thread serves the client and exits.
6. Both models hold one unit (process or thread) per client in flight, not per request per second.
7. Loop model: no new unit per client. One thread asks the kernel which sockets are ready (s03-m02-select).

**Rung 3, the real thing.**
- Slide 5 shows the fork echo server. It is the same code as Session 1 (s01-m06-many-clients). Backlog 1, the child echoes, the parent closes.
- `forkd.c` L29-35: the SIGCHLD handler reaps in a `waitpid(-1, NULL, WNOHANG)` loop, because one signal can stand for many dead children.
- `forkd.c` L60-66: fork fails with EAGAIN at RLIMIT_NPROC. L70-72: the child closes the listening socket. L14: kill the parent, and the children keep serving (S03-C168).
- `threadd.c` L68-70 prints the default stack. A scratch run on Fedora 44 printed `default thread stack: 8388608 bytes (8192 KiB)` and `x10,000 threads = 83.9 GB of address space`. The program divides by 10^9. The slide rounds 80,000 MiB to "80 GB". Both describe 78.1 GiB.
- The fork(2) man page says a fork costs the page-table copy and a task structure, because the pages are copy-on-write (`B10`).
- A scratch run of 1,000 idle threads grew VmSize by 7.8 GiB and VmRSS by only 8.2 MiB (`B06`, `B08`).
- A scratch run of forkd with 10 held connections showed 32 KiB Private_Dirty and a VmSize of 2,460 KiB per child (`B06`, `B10`).
- The goroutine side of slide 24 (2 KB stacks) is the memory wall in s03-m07-limits.

**Rung 4, exam depth.**
- *Why does thread per request still lose at 10,000?* Address space is not the first wall on 64-bit Linux. The walls are resident memory as stacks grow, kernel stacks (16 KiB each on x86-64, `B08`), scheduler work, and RLIMIT_NPROC, which counts threads (S03-C26). threadd calls the 80 GB "the reason nobody ships this", but slide 27 (Apache worker) and slide 29 (Varnish) ship a thread per connection (S03-C22).
- *Why did Go bring the thread model back?* A goroutine stack is about 4,096 times smaller (8 MiB / 2 KiB), and the runtime turns blocking reads into epoll waits. The programmer writes blocking code on top of a loop (s03-m07-limits).
- *What if you shrink the stack?* `STACK=65536` gives 64 KiB (S03-C23). Deep recursion or large local arrays then overflow into the guard page and crash.
- *Fork versus thread isolation.* A crash in a forked child kills one client. A crash in a thread kills the whole process. That is why prefork survived for non-thread-safe modules (S03-C138).

**Misconceptions.**
- S03-M01: "A thread costs 8 MB of RAM." Wrong. It reserves 8 MiB of address space. RAM grows only with touched pages. Distractor in check 2.
- S03-M02: "fork copies all parent memory before it returns." Wrong. Linux copies page tables and shares pages copy-on-write. Distractor in check 3.
- S03-M28: "After fork, parent and child share one address space, as threads do." Wrong. The child gets its own page tables. The first write to a shared page gives the writer a private copy (`B10`). Distractor in check 3.

**Diagrams.**
- Static: three columns (fork, thread, loop). Actors: client, kernel, process or thread. Each column stacks the per-client cost boxes: descriptor, stack, page tables, scheduler entry.
- Step-by-step: accept, fork, child serves, child exits, zombie, `waitpid`.

**Interactives.**

### s03-m02-select

- **Title:** Select: one thread, every client, and the 1024 wall.
- **Minutes:** 25.
- **Big idea:** Select lets one thread wait on many sockets, but it rebuilds its watch list on every call and cannot name a descriptor above 1023.
- **Covers:** S03-C12, S03-C32, S03-C33, S03-C34, S03-C35, S03-C36, S03-C37, S03-C38, S03-C39, S03-C40, S03-C41, S03-C42, S03-C43, S03-C44, S03-C45, S03-C46, S03-C47, S03-C48, S03-C49, S03-C50, S03-C166, S03-C167.
- **Prereqs:** s03-m01-threads-and-fork, s01-m02-ports-and-queue, s01-m03-signals-sigpipe.
- **Threads:** T-watch-list.

**Pretest.**
1. A select server watches only 10 clients, but one client has descriptor 1030. Can select watch it? *Answer: no. The limit is the descriptor number, not the count.*
2. Does `ulimit -n 65536` raise the select limit? *Answer: no. FD_SETSIZE is a compile-time bitmap width.*
3. After select returns, can you reuse the same set for the next call? *Answer: no. Select overwrites the set with the ready descriptors.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| Before each question, a teacher writes seat numbers on a fresh sheet with 1,024 boxes. | The loop fills an `fd_set` bitmap with descriptor numbers. |
| The office ticks the boxes of students with a raised hand and hands the sheet back. | The kernel keeps only the ready bits and returns. |
| A student in seat 1030 has no box, even in a class of ten. | Descriptor 1030 has no bit, even with ten clients. |

Where this breaks: the office does not look at all students at once. The kernel checks each descriptor in turn, and that walk is the O(n) cost.

**Rung 2, how it works.**
1. Clear the set. Add the listening socket and every client.
2. Remember the highest descriptor. Pass that number plus one.
3. Call select. It sleeps until at least one descriptor is readable.
4. Select rewrites the set. Only ready bits stay on.
5. If the listener is ready, accept one client and append it.
6. Walk the clients. Skip the ones that are not ready.
7. For a ready client, read. Zero or an error means the client left: close it and remove it. Otherwise write the bytes back.
8. Go to step 1. Build the set again.

**Rung 3, the real thing.** Walk `lesson3/01_echo_server_select.c` line by line.
- L1-4: headers. `sys/select.h` gives `fd_set`, the `FD_` macros and `select`.
- L7-13: TCP socket, all interfaces, port 2026 in network byte order (s01-m05-byte-order-dns), bind, listen with backlog 16. The code checks no return value.
- L15: `int clients[FD_SETSIZE]` is 1,024 ints (4,096 bytes) on the stack. L16: `nclients` counts the live entries.
- L19-20: a new `fd_set` each turn, cleared. On x86-64 glibc it is 16 words of 64 bits: 128 bytes, 1,024 bits.
- L21-22: watch the listener. Readable means `accept` will not block.
- L24-27: add each client and track `maxfd`.
- L29: `select(maxfd + 1, &readfds, NULL, NULL, NULL)`. The first argument is the highest descriptor plus one. No write set, no except set, no timeout.
- L31-33: a ready listener means one `accept`, appended at the end. The new descriptor is not in the set for this turn, so the walk skips it.
- L35-37: walk the clients, skip the ones without a bit.
- L39-40: read up to 4,096 bytes.
- L41-44: on 0 or -1, close, then the swap-remove. `clients[i] = clients[--nclients]` moves the last entry into the hole in O(1). Order does not matter. `i--` makes the next pass test slot i again, because the moved entry came from the unvisited tail.
- L46: echo the bytes with one blocking `write`.
- **The bit math.** FD_SET(fd) sets bit `fd % 64` of word `fd / 64`. Descriptor 130 is word 2, bit 2. Descriptor 1023 is word 15, bit 63. Descriptor 1024 would be word 16, which does not exist.
- **The real bugs**, in order of damage.
  1. L32 stores the result of `accept` with no check. At the descriptor limit `accept` returns -1 (EMFILE). FD_SET(-1) gives undefined behavior (`B01`).
  2. L32 has no bound on `nclients`. The waiting connection keeps the listener readable, so every turn appends another -1 and runs past the array.
  3. L25 has no `fd < FD_SETSIZE` check. With a higher ulimit, descriptor 1024 writes past the set into other stack variables.
  4. L29 ignores the return of select. On error the sets stay full (`B02`), so the loop treats every descriptor as ready and blocks in `accept` or `read`.
  5. L40 and L46 use blocking sockets. A client that stops reading fills its buffers, `write` blocks, and every client stalls (s03-m03-stacking-and-timeouts). Select can also report a socket readable, and then `read` blocks (`B04`). This bug shows that the repo README goes too far when it says the loop "never blocks on any single client" (S03-C167).
  6. L46 ignores the result of `write`. A write to a reset peer raises SIGPIPE and kills the whole server (s01-m03-signals-sigpipe).
  7. L12-13 ignore `bind` and `listen`, with no SO_REUSEADDR. If `bind` fails, `listen` binds a random free port (`B03`), and the server listens on the wrong port without a word.
- A scratch flood of this exact file showed bugs 1 to 3 (`B06`).
- `selectd.c` is the fixed version: the guard at L120-126, non-blocking sockets at L77 and L129, SIGPIPE ignored at L79, a bounded table at L60, a backwards walk at L139.

**Rung 4, exam depth.**
- *O(n) three times.* You build n bits, the kernel walks up to maxfd + 1 descriptors, and you walk n clients. With 10,000 idle and 10 active, that is 30,000 units of work for 10 events (S03-C45). Epoll keeps the watch list in the kernel and returns only ready events. The full comparison is s04-m05-select-vs-epoll.
- *Why is the limit a number, not a count?* The set is a bitmap indexed by descriptor number. A process that opened 1,020 files first gets socket 1024 for its first client.
- *Is the skip without `i--` a data loss?* Not with select. Select is level triggered, so the skipped socket shows as ready again on the next turn (`B30`). The cost is one extra turn of latency. With edge-triggered epoll the same skip can lose the only wake-up (Session 4).
- *One wall, three names (S03-C39, S03-C166).* The link between FD_SETSIZE and the default soft ulimit is causal: systemd keeps the soft limit at 1024 because select breaks above 1023 (`B11`). The slide also calls 1024 "the K in C10K". The K in C10K means one thousand, not 1,024 (`B29`). A quiz on the deck can use the slide phrase "one wall, three names". For a design answer, use 10,000.

**Misconceptions.**
- S03-M03: "Raising `ulimit -n` lets select watch more sockets." Wrong. The build fixes the bitmap width. Distractor in check 2.
- S03-M04: "FD_SETSIZE limits how many descriptors you watch." Wrong. It limits which numbers exist. Distractor in check 1.
- S03-M05: "Select remembers the watch list between calls." Wrong. It overwrites the set. Distractor in check 4.
- S03-M06: "The swap-remove works without `i--`, so the moved entry is tested in the same pass." Wrong. The moved entry skips one turn. Distractor in check 5.
- S03-M29: "FD_SET reports a descriptor out of range with an error." Wrong. FD_SET is a macro with no return value. Out of range is undefined behavior (`B01`), and a fortified build aborts (`B05`). Distractor in check 1.
- S03-M30: "Freeing low descriptors lets select watch a higher one." Wrong. The set still has 1,024 bits, and descriptor 2000 has no bit. Distractor in check 2.
- S03-M31: "Without `i--`, the moved client is never served." Wrong. Select is level triggered, so the bit is set again on the next turn (`B30`). Distractor in check 5.

**Diagrams.**

- Step-by-step: one loop turn with listener 3 and clients 4, 5, 7. Build, select, accept, walk, swap-remove.

### s03-m03-stacking-and-timeouts

- **Title:** Stack the models, and never wait forever.
- **Minutes:** 18.
- **Big idea:** Real servers run a loop inside each pre-forked worker, and each loop needs deadlines so that one slow client cannot freeze the rest.
- **Covers:** S03-C08, S03-C51, S03-C52, S03-C53, S03-C54, S03-C55, S03-C56, S03-C57, S03-C58, S03-C59, S03-C165.
- **Prereqs:** s03-m01-threads-and-fork, s03-m02-select.
- **Threads:** T-setup-off-path, T-watch-list, T-network-not-function.

**Pretest.**
1. Why fork workers at startup instead of per request? *Answer: the fork cost moves off the request path, and a crash kills one worker, not the server.*
2. A select loop has a 5-second timeout. A client stops reading while the server writes a large reply. Does the loop keep serving others? *Answer: no. The blocking write stalls the loop. The timeout only bounds the wait inside select.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| A manager hires four waiters when the restaurant opens. | The master forks one worker per CPU core at startup. |
| Each waiter walks their own section and stops at raised hands. | Each worker runs its own select or epoll loop. |
| A host at the door seats each new guest in some section. | SO_REUSEPORT lets the kernel spread new connections. |
| A waiter who waits at one table for a slow guest leaves the section alone. | One blocking call stalls every connection in that loop. |

Where this breaks: the kernel does not seat guests by who is least busy. It picks a socket from a hash, so a busy worker still gets its share (`B12`).

**Rung 2, how it works.**
1. At startup the master forks N workers, often one per core.
2. Each worker opens the listening socket or inherits it.
3. With SO_REUSEPORT, each worker has its own listening socket, and the kernel picks one for each new connection.
4. Each worker runs a loop over its own clients.
5. A crash kills one worker. The master starts a new one.
6. Each wait needs a deadline: select gets a timeout, each client gets an idle limit, each write waits in the write set, not in a blocking call.
7. The client side sets its own deadline and retries with backoff.

**Rung 3, the real thing.**
- Slide 8 names the stack: the Apache event MPM, nginx master and workers, the Go runtime.
- `SO_REUSEPORT` arrived in Linux 3.9 (`B12`). nginx uses it only with `listen ... reuseport`, since 1.9.1. The nginx details are s04-m03-process-model.
- The select signature from slide 9: `select(maxfd + 1, &readfds, &writefds, &exceptfds, &timeout)`. A NULL timeout blocks until a descriptor is ready. `struct timeval tv = {5, 0}` returns 0 after 5 s with nothing ready. Linux can change `tv`, so set it again each turn (`B02`).
- The sets, as select(2) and accept(2) define them: readable (data, a pending connection on a listener, or end of file), writable (a write will not block, or a non-blocking connect finished), exceptional (for example TCP urgent data). See `B03` for the slide wording.
- `selectd.c` L99-100 and L166-172 put a connection in the write set while it has output, and write only when select says writable. L77 and L129 make every socket non-blocking.

**Rung 4, exam depth.**
- *Why stack both?* Processes give crash isolation and use all cores. The loop gives thousands of connections per process. Threads per worker (Apache event, Varnish) add a pool for blocking work (S03-C140, S03-C149).
- *What wedges a loop?* Any blocking call on one socket: `read` after a false ready, `write` to a client that does not read, a DNS lookup, a disk read on a cache miss (S03-C154). The fix is non-blocking sockets plus an offload pool.
- *Why a timeout if nothing blocks?* To close idle clients and fire timers. Without it, a client that connects and sends nothing holds a descriptor forever. Many such clients use up the descriptor wall (s03-m07-limits).
- *Client half.* A deadline turns "the server is slow" into a clear error. A retry after a timeout can run the request twice (T-network-not-function), so retry only a request that is safe to repeat.
- *Slide wording against the man page.* Slide 9 says exceptfds waits for "sockets being connected and closed" (S03-C165). The Linux man pages say a close shows as readable, a finished connect as writable, and exceptfds reports urgent data (`B03`). Slide 9 also ties the frozen loop to the NULL timeout. The freeze comes from a blocking call, and a timeout does not stop it (S03-M07). A quiz on the deck can expect the slide wording. A design answer uses the man page behavior. Section 7, questions 4 and 6, record both conflicts.
- *No assignment code here.* The Session 5 calculator uses one persistent connection. This module gives concepts only. See s05-m12-assignment-prep.

**Misconceptions.**
- S03-M07: "A select timeout protects the loop from a client that stops reading." Wrong. The block happens in `write`, outside select. Distractor in check 1.
- S03-M08: "exceptfds reports sockets that connect or close." Wrong on Linux. A close shows as readable, a finished connect as writable. This is the slide 9 wording, so rung 4 shows both readings. Distractor in check 3.
- S03-M32: "A bigger listen backlog stops one slow reader from freezing the loop." Wrong. The backlog holds connections that wait for `accept`. The stall is in `write` to a client that the loop already serves. Distractor in check 1.
- S03-M33: "Select cannot see a closed peer. The loop learns only when a later write fails." Wrong. End of file makes the descriptor readable, and `read` returns 0 (`B03`). Distractor in check 3.

**Diagrams.**
- Static: master, four workers, one listening socket per worker, the kernel spreading connections. Label: crash isolation, concurrency.

### s03-m04-cgi

- **Title:** CGI: a new program for every request.
- **Minutes:** 20.
- **Big idea:** CGI turns an HTTP request into a process: headers become environment variables, the body goes to stdin, and the reply comes back on stdout.
- **Covers:** S03-C60, S03-C61, S03-C62, S03-C63, S03-C64, S03-C65, S03-C66, S03-C67, S03-C68, S03-C69, S03-C70, S03-C71, S03-C72, S03-C73, S03-C74, S03-C75, S03-C76, S03-C77, S03-C78, S03-C79, S03-C80.
- **Prereqs:** s03-m01-threads-and-fork, s01-m08-framing, s02-m09-ftp-framing.
- **Threads:** T-framing, T-setup-off-path.

**Pretest.**
1. How does a CGI script learn the HTTP method? *Answer: from the environment variable REQUEST_METHOD.*
2. Where does a CGI script read the POST body? *Answer: stdin.*
3. What separates the headers from the body in CGI output? *Answer: a blank line.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| For each order, a restaurant hires a new cook. | For each request, the server forks and execs the script. |
| The order sits on notes stuck to the cook: table 4, no salt. | The request details are environment variables. |
| Ingredients come through one hatch. Plates go out another. Complaints go to a box. | The body arrives on stdin. The reply leaves on stdout. Errors go to stderr. |
| After one plate the cook goes home. | The process exits after one request. |

Where this breaks: a new process starts in milliseconds, not hours. And the cook going home has an upside: nothing leaks from one request to the next.

**Rung 2, how it works.**
1. Apache reads the request line and headers.
2. It builds the environment: REQUEST_METHOD, QUERY_STRING, CONTENT_LENGTH, CONTENT_TYPE, SERVER_PROTOCOL, and one HTTP_ name per header.
3. It makes three pipes and forks.
4. The child moves the pipe ends onto descriptors 0, 1 and 2, then execs the script with that environment.
5. The parent writes the body into the stdin pipe and closes it, so the script sees end of file.
6. The script prints headers, a blank line, and the body, then exits.
7. The parent reads stdout up to the blank line, fixes the headers, and streams the rest to the client. Stderr goes to the error log.

**Rung 3, the real thing.**
- Slide 12 rule: `User-Agent: curl` becomes `HTTP_USER_AGENT=curl`. RFC 3875 §4.1.18 states the same rule (`B13`).
- RFC 3875 §4.1 lists 17 standard variables: AUTH_TYPE, CONTENT_LENGTH, CONTENT_TYPE, GATEWAY_INTERFACE, PATH_INFO, PATH_TRANSLATED, QUERY_STRING, REMOTE_ADDR, REMOTE_HOST, REMOTE_IDENT, REMOTE_USER, REQUEST_METHOD, SCRIPT_NAME, SERVER_NAME, SERVER_PORT, SERVER_PROTOCOL, SERVER_SOFTWARE. SCRIPT_FILENAME and REQUEST_URI are server extensions, not RFC names.
- Apache `server/util_script.c` (2.4.x): `ap_add_cgi_vars` starts at L401 and sets GATEWAY_INTERFACE at L409 (the slide line). `http2env` at L56 does the name rule. `ap_add_common_vars` at L174 maps Content-Type and Content-Length to CONTENT_TYPE and CONTENT_LENGTH, drops `Proxy`, and drops `Authorization` unless CGIPassAuth is on (`B14`).
- Apache `modules/generators/mod_cgi.c` (2.4.x): `run_cgi_child` starts at L345. It sets a pipe timeout on stdin, stdout and stderr at L444-455. The slide points at L576, see section 7.
- The syscalls live in APR `threadproc/unix/proc.c` (1.7.x): `fork` at L391, `dup2` onto 0, 1, 2 at L432-450, `chdir` to the script folder at L457, `execve` at L567 (`B15`).
- Slide 13 output, with the bytes: `Content-Type: text/html` CR LF, CR LF, then the body. A normal (parsed-header) script can add `Status: 404 Not Found` (RFC 3875 §6.3.3), and it does not print the status line. The exception is an NPH (non-parsed header) script. It writes the full HTTP response, status line included, and the server passes it on unchanged (RFC 3875 §5, `B13`).

**Rung 4, exam depth.**
- *Why pipes can deadlock.* A Linux pipe holds 65,536 bytes (`B15`). If the server writes a large body while the script writes large output and never reads its input, both sides block. The pipe timeouts in `run_cgi_child` bound the damage.
- *Why CGI lost.* fork, exec, and interpreter start run on every hit (S03-C75). The instructor estimate is 5 to 20 ms before your code runs (S03-C80).
- *Why mod_php won for a while.* No new process per request. The cost is one address space for server and language, so one segfault kills both (S03-C77).
- *Security of the name rule.* The header `Proxy:` becomes HTTP_PROXY, which many HTTP libraries read as their proxy setting (httpoxy, CVE-2016-5387 for Apache httpd). So Apache drops that header (`B14`).
- *Why names with underscores vanish in Apache.* `X-Api-Key` and `X_Api_Key` both map to HTTP_X_API_KEY. `http2env` drops any name with a character other than a letter, a digit or a dash, so a client cannot fake the dash form.
- *Threaded MPMs.* Forking a large threaded process is costly, so Apache recommends mod_cgid, a small daemon that forks the scripts (`B16`).

**Misconceptions.**
- S03-M09: "A CGI script prints `HTTP/1.1 200 OK` first." Wrong for a normal script. It prints header fields and a blank line, and the server writes the status line. Exception: an NPH (non-parsed header) script writes the full response, status line included (RFC 3875 §5, `B13`). Distractor in check 2.
- S03-M10: "A POST request has no QUERY_STRING." Wrong. Slide 16 shows POST with `QUERY_STRING = x=10`. RFC 3875 says the server must always set it. Distractor in check 3.
- S03-M11: "mod_php runs the language in a separate process." Wrong. It runs inside the server address space. Distractor in check 4.
- S03-M34: "The server adds Content-Type, so a CGI script prints only the body." Wrong. A document response must carry a Content-Type header (RFC 3875 §6.2.1, `B13`). Distractor in check 2.
- S03-M35: "For POST, the server moves the query string into stdin with the body." Wrong. Stdin carries only the body, CONTENT_LENGTH bytes. The query stays in QUERY_STRING (`B13`). Distractor in check 3.
- S03-M36: "A segfault in one request kills only that request." Wrong. The signal kills the whole process. Under mod_php, that is the Apache process and every connection on it (S03-C77). Distractor in check 4.

**Diagrams.**
- Static: the slide 10 flow. Actors: client, Apache, CGI process, error log. Arrows: envp, stdin pipe, stdout pipe, stderr.
- Step-by-step: `pipe`, `fork`, `dup2` × 3, `execve`, write body, read headers, blank line, stream body, `waitpid`.

**Interactives.**
- *Request to environment mapper.* P1. Input: raw HTTP request text. The script is the path up to and including the segment after `/cgi-bin/`. Output, as a pure function:
  1. The environment, in this fixed order: REQUEST_METHOD, QUERY_STRING (always, empty when the path has no `?`), CONTENT_TYPE and CONTENT_LENGTH (only when the header exists), SERVER_PROTOCOL, GATEWAY_INTERFACE=CGI/1.1, SCRIPT_NAME, PATH_INFO (only when a path follows the script), then one HTTP_ name per other header, in request order.

  The mapper does not make SERVER_NAME, SERVER_PORT, REMOTE_ADDR or other names that need the connection or the server config. Tests, with the expected output:

### s03-m05-fastcgi-servlets

- **Title:** FastCGI: keep the program alive, send it records.
- **Minutes:** 20.
- **Big idea:** FastCGI keeps a pool of workers alive and sends them the same CGI data as length-prefixed records on a socket.
- **Covers:** S03-C81, S03-C82, S03-C83, S03-C84, S03-C85, S03-C86, S03-C87, S03-C88, S03-C89, S03-C90, S03-C91, S03-C92, S03-C93, S03-C94, S03-C95, S03-C96, S03-C97, S03-C98, S03-C99, S03-C100, S03-C101, S03-C102, S03-C103, S03-C104, S03-C163.
- **Prereqs:** s03-m04-cgi, s01-m08-framing, s02-m09-ftp-framing.
- **Threads:** T-framing, T-setup-off-path, T-skip-unknown.

The servlet half of slides 15 to 19 moved to s03-m09-servlets (section 7, question 22).

**Pretest.**
1. How does a FastCGI receiver know where the params stream ends? *Answer: a params record with content length 0.*
2. How many bytes is a FastCGI record header? *Answer: 8.*
3. Which program parses the HTTP request, nginx or php-fpm? *Answer: nginx. php-fpm never parses HTTP (S03-C81).*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| A team of cooks stays in the back kitchen all day. | php-fpm keeps a pool of long-lived workers. |
| The front counter takes orders from slow customers. | nginx holds slow client connections, TLS and buffering. |
| Each order card says "order 1, 17 letters follow, 7 blank". | Each record header gives requestId, contentLength, paddingLength. |
| A blank card means "that part of the order is complete". | A zero-length record ends its stream. |

Where this breaks: the cards allow many orders on one trip, but nginx sends one order per connection.

**Rung 2, how it works.**
1. php-fpm starts a pool and listens on a socket.
2. nginx accepts the client and reads the HTTP request.
3. nginx opens a connection to php-fpm and sends a `FCGI_BEGIN_REQUEST` record.
4. It sends the CGI variables as name-value pairs in params records, then an empty params record.
5. It sends the body in stdin records, then an empty stdin record.
6. A worker runs the script. It sends headers, blank line and body in stdout records, then an empty stdout record.
7. Debug output goes in stderr records.
8. The worker sends `FCGI_END_REQUEST` with the exit status. nginx parses the headers and streams the body to the client.

**Rung 3, the real thing.**
- The header, from `fastcgi.h` L9-15 and FastCGI spec §3.3 (`B17`): `version(1) type(1) requestId(2, big-endian) contentLength(2, big-endian) paddingLength(1) reserved(1)`, then content, then padding.
- The `FCGI_BEGIN_REQUEST` record, from a scratch run of `fcgi_client` against `fcgi_responder`:

| Bytes | Field | Value |
|---|---|---|
| `01` | version | 1 |
| `01` | type | 1, `FCGI_BEGIN_REQUEST` |
| `00 01` | requestId | 1 |
| `00 08` | contentLength | 8 |
| `00` | paddingLength | 0 |
| `00` | reserved | 0 |
| `00 01` | role | 1, responder |
| `00` | flags | 0, close after the request |
| `00 00 00 00 00` | reserved | 0 |

- Params header `01 04 00 01 01 d0 00 00`: type 4, id 1, length 0x01d0 = 464, padding 0. The first pair is `11 07`, then `GATEWAY_INTERFACE` (17 bytes), then `CGI/1.1` (7 bytes).
- A long value: `12 80 00 00 c7` means name length 18, value length 199 in the 4-byte form (`fcgi_client.c` L117-122).
- Empty params `01 04 00 01 00 00 00 00`. Empty stdin `01 05 00 01 00 00 00 00`.
- The slide 16 body as a record: `01 05 00 01 00 11 07 00`, then the 17 bytes of `name=alice&age=20`, then 7 zero bytes.
- nginx parses this header with a byte-by-byte state machine, and refuses any requestId other than 1 (s04-m13-fastcgi-records, NGINX-TOUR Stop 10).

**Rung 4, exam depth.**
- *Length and delimiter in one protocol.* The length frames each record, so content can hold any byte. The empty record ends a stream of unknown length, so nginx can stream a body without knowing its size. HTTP chunked encoding has the same shape (s05-m04-range-chunked-extras).
- *Why padding?* Alignment to 8 bytes lets a reader take whole words. The receiver must skip `paddingLength` bytes, which the length makes easy.
- *Room for version 2.* A management record of an unknown type gets an unknown type reply, and a reader skips any record by its length (T-skip-unknown, `B17`).
- *Why nginx declines multiplexing.* With many requests on one connection, a slow reply blocks the others behind it. One request per connection, plus upstream keep-alive, avoids that coupling (NGINX-TOUR Stop 10, Session 4).
- *Project note.* The binary HTTP project must defend its own field widths. This module reads FastCGI choices as an example only, and gives no project spec (s05-m13-project-studio).

- S03-M13: "contentLength counts the header and the padding." Wrong. It counts only content bytes. Distractor in check 1.

### s03-m06-stateless-servers

- **Title:** Stateless servers, and where the state goes.
- **Minutes:** 15.
- **Big idea:** HTTP carries everything in each request, so any box can answer it, and that is why web tiers scale out while databases fight to keep connections.
- **Covers:** S03-C109, S03-C110, S03-C111, S03-C112, S03-C113, S03-C114, S03-C115, S03-C116.
- **Prereqs:** s02-m04-tcp-lifecycle, s03-m05-fastcgi-servlets.

**Pretest.**
1. Can a load balancer send request 2 to a different web server than request 1? *Answer: yes, if each request carries all it needs.*
2. Why does a Redis client keep its connection open? *Answer: a new connection costs a TCP handshake, auth and session setup, and state lives on the connection.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| Any vending machine sells you a drink, because you bring coins each time. | Any web server answers a request, because the request carries all it needs. |
| A bank teller checks your ID once and then knows you at that window. | A database connection holds auth and session state. |
| Walking to a new window means showing ID again. | A new connection costs connect, handshake, auth, setup. |

Where this breaks: a web app still has state, such as carts and logins. It moves that state into cookies, a database, or a cache. The state does not vanish.

**Rung 2, how it works.**
1. A client sends a request with the method, path, headers and body.
2. Any server in the pool can answer, because nothing depends on the last request.
3. The server can close the connection when it likes.
4. To grow, add a server to the pool.
5. The app stores its state in a database.
6. The database keeps state per connection, so clients hold long connections.
7. The capacity question becomes "how many open connections per box".

**Rung 3, the real thing.**
- Slide 20 lists what speaks HTTP (S03-C110) and what does not (S03-C111).
- Redis state per connection: a new connection always starts in database 0, and `SELECT` changes it for that connection only (`B28`).
- `selectd.c` L156-159 answers with `Connection: close`, then closes. Each request stands alone.
- HAProxy holds a pool of upstream connections to cut connects and disconnects (S03-C146, s03-m08-in-the-wild).

**Rung 4, exam depth.**
- *Why is stateless "free-ish"?* Scaling out still needs a load balancer, a shared session store and shared caches. The slide calls it free-ish, not free.
- *What changes for a database tier?* Connection count, not request rate, becomes the limit. Each connection costs a descriptor and memory (s03-m07-limits). So apps put a pool in front, which pays the setup once (T-setup-off-path).
- *Where does the state go next?* The deck closes with "go looking for state" (S03-C164). Sessions 4 and 5 preview Session 6, "Where did the state go?".
- *Protocol decides tricks.* Slide 20 puts MQTT brokers and messenger backends outside HTTP. Web advice that assumes stateless requests does not carry over to them (S03-C112). Little's law still does (s03-m07-limits).

**Misconceptions.**
- S03-M16: "Stateless HTTP means the application keeps no state." Wrong. The state moves to a store behind the web tier. Distractor in check 2.
- S03-M26: "HTTP keeps the session on the TCP connection, so the next request must reach the same box." Wrong. Each request carries its own context, such as a cookie. Sticky routing is a choice, not a rule of HTTP. Distractor in checks 1 and 2.

### s03-m07-limits

- **Title:** The four walls, and the law that links them.
- **Minutes:** 25.
- **Big idea:** Every connection you hold spends from four budgets (descriptors, memory, kernel crossings, time in the queue), and the fourth sets how many you hold: arrival rate times latency.
- **Covers:** S03-C21, S03-C22, S03-C28, S03-C29, S03-C30, S03-C31, S03-C117, S03-C118, S03-C119, S03-C120, S03-C121, S03-C122, S03-C123, S03-C124, S03-C125, S03-C126, S03-C127, S03-C128, S03-C129, S03-C130, S03-C131, S03-C132, S03-C133, S03-C134, S03-C135, S03-C136.
- **Prereqs:** s03-m01-threads-and-fork, s03-m02-select.
- **Threads:** T-littles-law, T-watch-list.

Segments: descriptors, memory, the kernel boundary, the queue. Each wall is one segment of about 5 minutes.

**Pretest.**
1. What does `ulimit -n` print on most distributions? *Answer: 1024, the soft limit.*
2. 1,000 requests per second, 200 ms each on average. How many requests are in flight? *Answer: 200.*
3. A config change doubles the thread pool. Do fewer requests sit in flight? *Answer: only if requests were waiting for a free thread. A bigger pool removes queue wait. It cannot push L below λ × service time.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| A hotel desk hands out 1,024 room keys by default. | A process gets 1,024 descriptors by default. |
| Each guest needs a room, even while asleep. | Each connection needs a buffer, and a stack if it has a thread. |
| For every towel, a guest rides the lift to the desk and back. | Every read and write crosses into the kernel and back. |
| One guest arrives each minute and stays 20 minutes, so about 20 guests are inside. | L = λ × W: requests in flight. |

Where this breaks: a lift ride takes a minute, but a syscall takes "hundreds of nanoseconds" (slide 25), so the tax only hurts at a million trips a second. And the law uses long-run averages. At one instant the count jumps around, and if guests arrive faster than rooms free up, the count never settles.

**Rung 2, how it works.**
1. Each socket takes one descriptor. At the soft limit, `accept` fails with EMFILE, and the connection waits in the accept queue.
2. A process can raise its soft limit up to the hard limit.
3. Each connection holds a buffer. A thread per connection adds a stack of address space (s03-m01-threads-and-fork). A goroutine starts with 2 KB.
4. Each `read` or `write` enters the kernel and returns. Calls per second times the cost of one call gives the CPU share.
5. Two escapes from that tax: make fewer calls (sendfile, io_uring batches), or skip the kernel network stack (DPDK and friends).
6. Requests in flight, L, equal the arrival rate λ times the mean time per request W.
7. If W grows 10 times at the same λ, L grows 10 times, and the descriptors and memory grow with it.
8. If L passes the pool size, requests queue, W grows again, and L grows again. To cut L, make the work faster or move slow work off the request path.

**Rung 3, the real thing.**
- *Descriptors.* `ulimit -Sn` and `ulimit -Hn` print the soft and hard limits. `/proc/PID/limits` shows them for a running process, and `prlimit --nofile` changes them. The kernel start values are 1024 soft and 4096 hard (`INR_OPEN_CUR`, `INR_OPEN_MAX`). systemd sets `DefaultLimitNOFILE=1024:524288` (`B11`). A shell in a terminal app can show a higher number, so check yours.
- *Memory.* Slide 24: a goroutine starts at 2 KB, 4,096 times smaller than 8 MiB. The Go runtime parks a blocking read on its netpoller in `src/runtime/netpoll_epoll.go` (slide 32). Since Go 1.19 the start size follows average use (`B09`). The thread side is in s03-m01-threads-and-fork.
- *Kernel boundary.* The slide 25 step "switch page tables" happens only with page table isolation, the Meltdown mitigation (`B20`). `sendfile(out_fd, in_fd, offset, count)` copies file bytes to a socket inside the kernel (slide 30, s04-m06-sendfile).
- *The queue.* Slide 26: at 100 ms, 1,000 connections. At 1 s, 10,000. The slide does not state the traffic. Both numbers imply 10,000 requests per second. John D. C. Little proved L = λW in 1961 for a stable system and long-run averages (`B21`).
- `forkd.c` L82-84 sleeps 2 s per request "so you can actually SEE" it, so W is about 2 s.
- NGINX-TOUR Stop 9 asks what happens when one app server gets 10 times slower, and says "Session 3 called it". That question belongs to s04-m10-upstreams.

**Rung 4, exam depth.**
- *C10K then and now.* In 1999, 10,000 connections was hard for common designs such as a process per client or select. The C10M manifesto (2013) moves packet work out of the kernel. In 2012 WhatsApp reported over 2 million TCP connections on one FreeBSD box (`B26`).
- *Why is the soft limit still 1024?* Programs that use select break above descriptor 1023, so systemd leaves the soft limit low. Programs that avoid select raise it themselves (`B11`).
- *A syscall is not a context switch.* A syscall is a mode switch in the same thread. A context switch runs another thread (`B31`). Slide 22 names the wall "context switches", and a blocking call does cause one when the thread sleeps.
- *Kernel bypass trade-off.* DPDK owns the NIC from user space. You lose `tcpdump`, `ss`, iptables and the kernel TCP stack (S03-C129).
- *Batching math.* 1,000,000 operations with 32 per io_uring submit need 31,250 syscalls. At 300 ns, a round value picked from the slide range "hundreds of nanoseconds", that is 9.4 ms of crossing per second instead of 300 ms. A scratch run on a newer CPU timed a simple syscall at 59 to 89 ns (`B20`).
- *Why a bigger pool has a floor.* The pool caps how many requests run. It does not change λ or the upstream time. If requests wait for a free thread, W holds that wait, and a bigger pool removes it, so L drops. L cannot drop below λ × service time. Example: λ = 1,000 per second and 1.55 s of service need 1,550 busy slots. A pool of 500 serves at most 500 / 1.55, about 323 per second, so L grows without limit. A pool of 2,000 lets L settle near 1,550. A pool of 4,000 still gives about 1,550.
- *Why async helps.* A background job cuts W for the request. The job still uses resources, but in a queue you can size and shed (S03-C134).
- *Mean, not p50.* W is the mean. With a long tail, the mean sits above p50, so a p50 estimate is too low (`B21`).
- *Memory view.* 1,550 requests in flight on threads with 8 MiB stacks reserve 12,400 MiB of address space. At 200 in flight it was 1,600 MiB.
- *Stability.* If λ is above the service rate of the pool, no steady state exists. L grows until a wall (descriptors, memory, timeouts) stops it.

**Misconceptions.**
- S03-M17: "1024 descriptors is a hard kernel maximum." Wrong. It is a soft default, and the hard limit under systemd is 524288. Distractor in check 4.
- S03-M18: "A syscall is a context switch to another process." Wrong. It is a mode switch in the same thread (`B31`). Distractor in check 6.
- S03-M19: "A bigger pool lowers L below λ × service time." Wrong. L = λW. A bigger pool can remove the wait for a free thread, but it cannot shorten the service time. Distractor in check 2.
- S03-M20: "Use p50 latency for W." Wrong. W is the mean. Distractor in check 3.
- S03-M40: "A higher descriptor limit lowers the requests in flight." Wrong. The limit only lets the server hold more. L = λW does not change. Distractor in check 2.
- S03-M41: "Use p99 latency for W to be safe." Wrong. The law needs the mean, and p99 predicts too many requests in flight. Distractor in check 3.
- S03-M42: "FD_SETSIZE limits an epoll server too." Wrong. epoll uses no `fd_set`. The wall for an epoll server is the descriptor limit. Distractor in check 4.
- S03-M24: "C10K means 10 × 1024 connections." Wrong. It means 10,000. Distractor in check 6.
- S03-M25: "sendfile bypasses the kernel." Wrong. sendfile is a syscall, and the copy stays inside the kernel. DPDK bypasses the kernel network stack. Distractor in check 6.

**Diagrams.**
- Static: the four walls from slide 22 as four boxes around one connection. Labels: descriptor, stack and buffer, kernel crossing, time in the queue.

**Rung 2, how it works.**
1. Apache prefork: one process per connection.
2. Apache worker: one thread per connection, idle keep-alive included.
3. Apache event: a listener thread parks idle sockets on epoll. A worker thread runs only when a socket has work.
4. HAProxy: one event loop in one process, select first, epoll from 2005.
5. Varnish: worker threads for active connections, a waiter loop for idle ones.
6. nginx: one master, one single-threaded epoll loop per worker, sendfile for files, a thread pool for disk reads.
7. All four: the loop waits, a worker works.

**Rung 3, the real thing.**

- HAProxy CHANGELOG: 1.0.0 on 2001-12-16. Experimental epoll in 1.2.5-pre3, 2005-04-25. 1.8.0 with threads on 2017-11-26. epoll(7) history: Linux 2.5.44 (`B23`).

- nginx: `sendfile on;` and `aio threads;` (1.7.11, needs `--with-threads`). `worker_processes auto;` gives one worker per core. The default is 1 (`B25`).
- Slide 30 contrast, as calls: `read(file_fd, buf, n); write(sock_fd, buf, n);` against `sendfile(sock_fd, file_fd, NULL, n);`.

**Rung 4, exam depth.**
- *The keep-alive problem.* With keep-alive, most connections sit idle between requests. A thread per connection pays a stack for idle time. The event MPM gives the thread back while the socket waits (S03-C139, S03-C140).
- *The timeline explains the design.* HAProxy picked select because epoll came later (T-law-or-habit). When the constraint went away, HAProxy moved to epoll and later added threads.
- *Threads for work, a loop for waiting.* Blocking work (disk, VCL, a slow backend) needs a thread. Waiting needs only a descriptor in a loop. Varnish, Apache event and nginx with `aio threads` all make this split.
- *Little's law per model.* At 10,000 connections, mostly idle: prefork holds 10,000 processes, worker holds 10,000 threads, event holds one loop plus threads for the active ones (s03-m07-limits).
- *First reverse proxy?* Slides 29 and 30 call Varnish the first popular caching reverse proxy and nginx the first reverse proxy. Squid already had an accelerator mode, and the 2006 Varnish test site also ran a Squid cache tier (`B24`).

### s03-m09-servlets

- **Title:** Servlets: the server is the runtime.
- **Minutes:** 15.
- **Big idea:** A servlet container keeps one object per servlet alive in one JVM and runs each request on a pool thread, so it pays the setup once, but every request shares one heap.
- **Covers:** S03-C105, S03-C106, S03-C107, S03-C108, S03-C161.
- **Prereqs:** s03-m05-fastcgi-servlets, s03-m01-threads-and-fork.
- **Threads:** T-setup-off-path.

**Pretest.**
1. Does a servlet container create a new servlet object per request? *Answer: no. One object per servlet declaration, shared by pool threads.*
2. In a Tomcat deployment, which program forks per request? *Answer: none. Tomcat is the web server, and a thread pool runs the requests.*

**Rung 1, the picture.**

| The picture | The real thing |
|---|---|
| A restaurant has its front counter and its kitchen in one building. | Tomcat or Jetty is the web server and the runtime, in one JVM. |
| Cooks wait on a bench from the time the restaurant opens. | A thread pool starts with the server. |
| An order goes to a free cook, who uses the one shared recipe book and then sits down again. | A request goes to an idle thread, which runs the one servlet object and returns to the pool. |
| All cooks share the pots. | All threads share one heap. |

Where this breaks: a cook sees a dirty pot and waits. Two threads do not see each other. They can change one field at the same time and lose an update. And one cook who takes all the pots stops the kitchen: one runaway servlet hurts its neighbours.

**Rung 2, how it works.**
1. The container starts the JVM, loads the servlet classes through a class loader, and starts a thread pool.
2. It makes one object for each servlet declaration and calls `init` one time.
3. A request arrives. The container parses the HTTP and gives the request to an idle pool thread.
4. The thread calls `service` on the shared servlet object, with a request object and a response object.
5. The thread writes the response and returns to the pool.
6. A second request at the same time runs `service` on the same object, on another thread.
7. No process separates the servlets. A class loader separates their classes, and each thread has its own stack. The heap is shared.

**Rung 3, the real thing.**
- Servlet spec §2.2: one servlet object per declaration. §2.3.2: `init` runs once. §2.3.3.1: many threads can run `service` at the same time (`B19`).
- `threadd.c` is the same model in C: a thread per request in one process. Its `live_threads` counter (L31, L37, L52) is one variable that every request sees. threadd changes it with an atomic add. S03-Q10 asks what happens without one.
- Slide 19 links pre-threading to the pre-forking of block 01 (S03-C106). Slide 34 lists servlets as one way to "amortise the setup" (S03-C161).

**Rung 4, exam depth.**
- *Servlet trade-off.* Threads cost less than processes, but threads share one heap. A servlet field that one request writes is visible to every other request (S03-C107, `B19`). Keep request data in local variables or in the request object.
- *Four answers to the slide 19 question.*

| Design | Setup paid | What runs a request | Isolation |
|---|---|---|---|
| CGI | per request (S03-C75) | a new process | a process |
| mod_php | once | an Apache process or thread | none from the server (S03-C77) |
| FastCGI | once (S03-C78) | a long-lived worker process | a process, apart from the web server |
| Servlet | once (S03-C106) | a pool thread | a class loader and a thread (S03-C107) |

- *What if the pool is full?* Requests wait for a free thread, and that wait adds to W (s03-m07-limits).
- *Why no httpd in front?* The JVM already runs your code, so nothing needs to fork (S03-C105).

**Misconceptions.**
- S03-M15: "A servlet container creates one servlet object per request." Wrong. One object, many threads. Distractor in check 1.
- S03-M46: "A servlet runs one request at a time." Wrong. Many threads can run `service` on the one object at the same time (`B19`). Distractor in check 1.
- S03-M47: "Each servlet runs in its own process, as a CGI script does." Wrong. Servlets share one JVM process (slide 19). Distractor in check 2.
- S03-M48: "Class loader isolation protects neighbours as well as a process does." Wrong. Slide 19 says one runaway servlet can still hurt its neighbours. Distractor in check 2.
