**Graded work.** This page prepares you for the calculator assignment, 20% of the grade. It gives a checklist, a test plan and hints, but no solution code. The instructor's course repo holds a finished HTTP/1.1 server, `server11.py`, and the lab below shows where it is. <SlideLink session={5} page={3}>The assignment slide</SlideLink> asks you not to read that file until your own server fails at least once.

The assignment asks for a small server, a program that answers requests over the network. It adds, subtracts, multiplies and divides two numbers. The math takes a few minutes. The hard part is one question: when one connection brings many requests, where does one request end and the next one start? This lesson answers that question. Then it gives each request its status code, the number at the start of each answer that says how the request went.

The question matters because of how the marker tests your server. The marker is the test program that grades your work. It opens one connection, sends six requests on it, and then checks that the connection is still open. An HTTP/1.0 server, the kind from 1996, hung up after each answer, so the close marked the end for free. Your server keeps the connection open, so it must find every end itself. The assignment is due before Session 7.

You already know two things that this lesson uses. From <ModuleLink id="s01-m08-framing" />, you know that TCP keeps every byte in order but keeps no mark where one message stops. From <ModuleLink id="s05-m02-keepalive-host" />, you know that an HTTP/1.1 connection stays open for many requests. The top of this page also names two threads. A thread is an idea that comes back in many lessons. Framing asks where a message ends. Setup off path means that you pay a costly setup, such as a new connection, one time and not for each request.

**The path through this lesson.** Part 1 reads two requests byte by byte and finds where each one ends: at an empty line, then after the data bytes, the body, that Content-Length gives. Part 2 shows why a server cannot see those ends in its reads, the pieces of bytes that it takes from the connection one at a time. It also shows what the server does with the bytes that are left over. Part 3 gives each request of the assignment its status code, and shows why the error answers of the marking run must leave the connection open.

<Segment title="Where one request ends">

**In this part.** You learn the two marks that end an HTTP/1.1 request: the empty line after the head, and the body size in Content-Length. A server that misses one of these marks mixes two requests into one. Part 2 then shows why the marks are hard to find in real reads.

<ReadingAnimation slot="visual" />

<Picture breaks="on paper, the cook can see where a note ends. In bytes, a body can hold anything, even an empty line. So the server counts the body bytes and never searches them for an end.">

At a school fair, a printer in the kitchen prints every food order on one long strip of paper, like a very long shop receipt. Nothing cuts the strip between two orders. Each order starts with a line that says what to make, such as "MAKE pancakes". A few short lines follow, such as "TABLE: 4", and sometimes "NOTE: 5 letters". Then the printer leaves one line empty. If the order has that note line, exactly 5 letters follow, such as "hello", to write on the plate. The letter after them starts the next order. The cook reads down the strip and finds where each order stops.

In HTTP, the strip is the connection, and each order is one request. The cook is your server. The first line, "MAKE pancakes", is the request line, and the short lines after it are the header lines. "TABLE: 4" is like the Host line, which says which website the request is for. The empty line ends the head. "NOTE: 5 letters" is the header line `Content-Length: 5`, and the 5 letters are the 5 bytes of the body. An order with no note line has nothing after its empty line. In the same way, a request with no Content-Length has no body.

</Picture>

### How it works

Now read like the cook, but with real bytes. The first word of a request line is the method, the action that the client wants. The client is the program that sends the request. GET asks for something, and POST sends data. The next part is the path, the name of the thing asked for. The Host line names the website, and every HTTP/1.1 request must carry one.

The animation shows the two requests of this lesson: a POST with the 5-byte body `hello`, then a GET for the path `/style.css`. A row ends after each `\r\n`, so the body `hello` shares a row with the request line of request 2. The number at the start of a row is the byte number of its first byte. Bytes count from 0.

<ScrollStep step={1}>

The connection brings 114 bytes, from byte 0 to byte 113. Nothing between the two requests marks an edge. The first byte of request 2 comes right after the last body byte of request 1.

</ScrollStep>

<ScrollStep step={2}>

First, find the end of the head. Every line of the head ends in the two bytes CR and LF, written `\r\n`. After the request line and the header lines, the head ends at a line that holds nothing before its `\r\n`. In request 1, that empty line is bytes 60 and 61.

</ScrollStep>

<ScrollStep step={3}>

Next, look in the head for Content-Length. Request 1 has the line `Content-Length: 5`. So its body is the 5 bytes right after the empty line.

</ScrollStep>

<ScrollStep step={4}>

Count those 5 bytes: h, e, l, l, o, bytes 62 to 66. Request 1 ends at byte 66. Byte 67 is the G of GET, and it starts request 2.

</ScrollStep>

<ScrollStep step={5}>

Request 2 has no Content-Length line. A request with no body size has no body. So request 2 ends with its own empty line, at byte 113.

</ScrollStep>

<KeyIdea id="empty-line-then-content-length" title="The empty line ends the head, Content-Length ends the body">

A request head ends at the empty line after its header lines. If the head says `Content-Length: n`, exactly n body bytes follow. The byte after them starts the next request.

</KeyIdea>

### The real thing

<SlideLink session={5} page={3}>The assignment slide</SlideLink> calls this "the part that is actually hard". The arithmetic is not the point. On a kept connection, the server takes exactly the bytes that Content-Length gives, and it stops there. The byte after them is already a part of another request.

<Beyond source="RFC 9112 §6.3" url="https://www.rfc-editor.org/rfc/rfc9112#section-6.3">

RFCs are the official documents that define internet protocols, and RFC 9112 defines how HTTP/1.1 looks on the wire. A request can send its body in chunks, with the header line `Transfer-Encoding: chunked`. The lesson <ModuleLink id="s05-m04-range-chunked-extras" /> teaches chunks, and the assignment lists them only as an optional extra, a stretch goal. A request with a valid Content-Length and no Transfer-Encoding has a body of exactly that many bytes. A request with neither header has no body.

</Beyond>

<ExamDepth>

**Why an HTTP/1.0 server never needed this.** <SlideLink session={5} page={7}>An HTTP/1.0 server</SlideLink> closed the connection after one answer. No second request came on that connection, so the close told the client where the answer ended. On a kept connection nobody closes, so only the empty line and Content-Length mark the ends.

**What if Content-Length does not match the body?** Say that a client writes 5 and sends 6 body bytes. The server takes 5 bytes, and the sixth byte looks like the first byte of the next request. That request is then broken. The lesson <ModuleLink id="s05-m05-rfcs-and-smuggling" /> shows how an attacker uses two readings of one length.

</ExamDepth>

<Segment title="A read is not a request">

**In this part.** Part 1 found the ends of two requests with all 114 bytes in view. A real server never sees the bytes that way. It gets them in reads, and a read can stop anywhere. This part shows what a server does with a read that holds half a request, or parts of two. The server keeps those extra bytes in a buffer, the bytes that it read but did not use yet.

<BoundaryFinder slot="visual" />

<Picture breaks="the cook can see that the printer still prints. A server cannot see whether more bytes are on the way. Its read can also stop in the middle of a line, even between the CR and the LF of the empty line.">

Now the strip comes out of the printer slowly. The cook does not wait for the whole strip. Every so often, the cook tears off the piece that has come out so far. One piece can hold half of an order. The next piece can hold the rest of that order and the start of the next one. So the cook never treats a piece as one order. The cook pins the unfinished part on a board and joins it to the next piece.

In the server, the printer is the client, which sends the bytes over TCP. Each torn piece is one read: one call, such as `recv()`, that takes the bytes that have arrived. The board is the buffer, the bytes that the server read but did not use yet. The cook finds orders by their lines and notes, not by the tears. In the same way, the server finds each request end with the two marks of Part 1, not with its reads.

</Picture>

### How it works

The finder uses the same two requests as Part 1. It cuts them into reads of the sizes that you type. Press Next to get one read at a time. Before each press, say whether the next read finishes a request.

With the sizes 30, 50 and 34, read 1 stops inside the Host line of request 1. Read 2 finishes request 1, and it also brings the first 13 bytes of request 2. Those 13 bytes stay in the buffer, and read 3 completes request 2.

Now type other sizes. With 4096, one large read brings both requests. With 61, read 1 stops after the CR of the empty line, so the head is not complete yet. With 1, each read brings one byte.

After the last byte, the finder stops. A real read waits for more bytes, because the client keeps the connection open. Only when the other side closes the connection does a read return no bytes at all. That signal is called end of file.

<KeyIdea id="a-read-is-not-a-request" title="A read is not a request">

One read gives the bytes that arrived: a part of a request, one request, or parts of two. The server keeps the bytes that it did not use, because they start the next request.

</KeyIdea>

### The real thing

<Beyond source="recv(2), the Linux manual page" url="https://man7.org/linux/man-pages/man2/recv.2.html">

The Linux manual page for `recv()` says that `recv()` and the calls like it "return any data available, up to the requested amount". So `recv(4096)` gives the bytes that wait, from 1 byte up to 4096 bytes. It does not wait for one whole request.

</Beyond>

The sender does not choose where your reads stop. The network carries the bytes in pieces, called packets. TCP and the timing of those packets decide how many bytes wait when a read runs. So a test must send a request in pieces on purpose. The test plan at the end of this page does that.

<ExamDepth>

**Why a small request is not safe.** A 47-byte request fits in one read of 4096 bytes. But a read returns only what arrived at that moment, so the 47 bytes can come in two reads. A slow client, a busy network, or a test that sends one byte at a time all cause it.

**What if many requests come in one read?** <SlideLink session={5} page={3}>The assignment slide</SlideLink> names this case as a stretch goal: take all six requests at once, and answer them in order. The order matters, because Part 3 shows that an answer carries no request number.

</ExamDepth>

<Picture breaks="a kid reads the words on the slip. A program acts on the number, so the number must be right, whatever the words say.">

At a school snack counter, kids ask for things one after another. Every kid gets a slip with a number at its top and a short note under it. A kid asks for 2 apples, gets them, and the slip says "200: done". A kid asks for "x" apples, and the slip says "400: that is not a number". A kid asks to share 1 apple among 0 friends, and the slip says "400: that cannot be done". A kid asks for pizza, and the slip says "404: we have no pizza". The counter is your server, and the line of kids is the requests on one connection. Each slip is an answer, and the number at its top is the status code. A bad order, such as "x" apples or a share among 0 friends, is bad input: 400. Pizza is a path that does not exist: 404. Selling to a counter that only gives out apples is a method that the path does not allow: 405. The note "only gives out apples" is like the Allow line of a 405 answer, which lists the methods that the path takes. The counter does not close after a wrong order, and your server keeps the connection open after these errors.

</Picture>

### How it works

The calculator gets its numbers in the request line. In `GET /add?a=2&b=3`, the method is GET and the path is `/add`. The part after the `?` is the query: it gives the numbers as `a=2` and `b=3`, joined by `&`.

<KeyIdea id="status-by-what-is-wrong" title="Pick the status by what is wrong">

Bad input, such as `b=0` for div or a value that is not a number, gets 400. A request with no Host line also gets 400. A path that does not exist, such as `/pow`, gets 404. A method that a real path does not allow, such as POST on `/add`, gets 405.

</KeyIdea>

Now try the picker. It holds the requests of <SlideLink session={5} page={3}>the assignment slide</SlideLink>. Pick up a request, drop it on a status, and read what the feedback says is wrong. Two statuses in the picker are traps, 500 and 501. They sound right, but they mean something else.

<Beyond source="RFC 9110 §15.6.1, §15.6.2" url="https://www.rfc-editor.org/rfc/rfc9110#section-15.6.1">

**Why not 500 for a division by zero?** RFC 9110, the document that defines what each status code means, keeps 500 for an unexpected condition inside the server. A division by zero comes from the client input, and the server can see it before it divides. So the answer is 400.

**Why not 501 for POST?** RFC 9110 uses 501 when the server does not know the method for any path. Your server knows POST as a method. Only `/add` refuses it, so the answer is 405.

</Beyond>

### The real thing

The assignment slide gives the whole feature set. Build the server on a plain socket, the end of a connection that the operating system gives your program. Use any language, but no framework, a ready-made web server library. The marker reaches your server through a port, the number that picks one program on a machine. Use this table as your checklist.

<KeyIdea id="six-answers-on-one-connection" title="Six answers on one connection">

The marker connects to port 8080 on your machine. It sends six requests on one connection: rows 1, 2, 3, 5, 7 and 8, in that order. Three of them are errors. Then the marker checks that the connection is still open: one connection setup (one TCP handshake), six answers.

</KeyIdea>

The slide says it plainly: if the connection dies before the marker is done, you wrote "a 1996 server". HTTP/1.0 is from 1996, and it closes after each answer. So the 400, the 404 and the 405 of the marking run are normal answers. The server sends each one and waits for the next request on the same connection.

The slide also lists four stretch goals, all optional. Close the connection when the client sends `Connection: close`. Pick an idle timeout that you can defend: how long the server waits for the next request before it closes the connection. Support chunked encoding. <SlideLink session={5} page={16}>In chunked encoding</SlideLink>, each chunk starts with its size in hex (base 16, with the digits 0 to 9 and a to f), and a chunk of size 0 ends the body. The assignment slide does not say whether it means requests, answers or both. Answer six requests that arrive at once, in order.

<Beyond source="RFC 9110 §15.5.6, RFC 9112 §3.2" url="https://www.rfc-editor.org/rfc/rfc9110#section-15.5.6">

A 405 means that the server knows the method, but the target path does not support it. The answer must carry an Allow header with the methods that the path supports. RFC 9112 §3.2 also requires a 400 for an HTTP/1.1 request with no Host header.

</Beyond>

<ExamDepth>

**Errors on a kept connection.** The marking run holds three errors: a 400, a 404 and a 405. The connection must stay open through all of them. The slide does not say what must happen after the no-Host 400 or the `a=x` 400. Test those two cases on separate connections, and ask the instructor.

**The idle timeout.** A short idle timeout frees server memory, but it drops a slow client. A long timeout keeps idle connections open. The lab server closes a connection that stays idle for 15 seconds. Its answers carry the line `Keep-Alive: timeout=15, max=100`. The first value tells the client about that timeout. The lab code does not enforce the second value, a limit of 100 requests. Pick your own number, and be ready to defend it.

**Answers in order.** If six requests arrive at once, the answers go back in the same order. An HTTP/1.1 answer carries no request number, so the client matches each answer to a request by its position. RFC 9112 §9.3.2 requires the same order.

**Why every answer needs its own length.** The client also reads a kept connection. Without a length on the answer, a Content-Length or chunked encoding, the client cannot find where the answer ends.

</ExamDepth>
