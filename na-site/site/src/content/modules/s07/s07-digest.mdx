A function call ends in one of two ways. It returns a value, or it raises. A remote call has a third ending: nothing comes back at all, and you cannot tell whether the work ran. This class is about that third ending, and about the four endings next to it. The deck states the discipline as one line on <SlideLink session={7} page={6} />: fail on purpose.

Two mistakes sit on opposite sides of one decision. The cheap one gives up on work that would have worked a moment later. The expensive one hammers a sick server until it dies, then hammers it again the second it comes back. Both come from the same gap: a failure that nobody named. So the repair is exact. Name the failure first, then choose the response.

**The path through this read.** Part 1 puts every failure of the class on the timeline of one request, and adds one new question to every status code. Part 2 gives the exact meaning of "retry", then sorts a failure into retry, handle or stop. Part 3 builds the safe loop: a cap, a growing delay, real randomness, and a breaker one level above all three. Part 4 turns the lens on a video player, where the right answer is often a different source. Part 5 asks what a whole system does when nothing healthy is left.

<Picture breaks="a letter leaves a paper trail. A lost response leaves none, so your program never learns which of the six stories it is in. Only the stage name in your log can tell it.">

You post a letter to a friend in another town. Six things must work: the address book, the post office, the seal, the van, your friend reading it and writing back, and the reply reaching your letterbox. A week passes and no reply comes. In one story the address book was wrong, so the letter never left your town. In another story your friend read it, acted on it, and the reply burned in a sorting fire. Posting the same letter again is fine in the first story and terrible in the second.

The address book is DNS, the post office is the TCP handshake, and the seal is TLS. The van leaving is the moment your bytes go out, your friend acting is the server doing the work, and the reply in your letterbox is the response you read.

</Picture>

<KeyIdea id="the-stage-decides" title="Nothing fails generically">

A request fails at one named stage of six, and the stage decides whether a retry can possibly help. A failure before the handshake never reached a server, so no server failed. A failure after your bytes went out can hide finished work.

</KeyIdea>

Every failure of this class sits on one line of six stages, and <SlideLink session={7} page={10} /> draws it as one arrow. The first three end before any server reads a byte of yours. The last three can leave a row written, an email sent or a card charged, with no answer to tell you so. That is why the stage matters more than the exception type. Two code paths can raise the same timeout error, and only one of them proves that no work started.

Class 5 taught what each status class means. This class adds one question to all of them, and <SlideLink session={7} page={11} /> puts it in a new column: will anything be different next time? A 1xx is interim, so keep listening. A 2xx means the server did the thing. A 3xx says to ask somewhere else, so the answer depends. A 4xx means the server refuses those same bytes every time you send them unchanged. A 5xx means the server admits that it failed. That question is the entire retry decision.

<Myth myth="A timeout is a timeout, so one handler can cover all of them.">

A DNS timeout and a read timeout write the same word and are completely different problems. The DNS timeout never reached a server, so a retry of the same broken path only burns the time twice. The read timeout had a socket and then went quiet, so a server saw your request and may have half-done the work. Log the stage name next to the word, or every later decision is a guess.

</Myth>

<Myth myth="A 500 proves that the server changed nothing.">

A 5xx tells you one fact only: the server knows that it failed. It says nothing about whether the server wrote a row, sent an email or charged a card before it failed. The class is a prior, not a rule, in the other direction too. The deck itself names two retryable 4xx codes later, 408 and 429, so read the code and not only its first digit.

</Myth>

<Myth myth="The class 1 client and the class 1 echo server on the slides connect to each other.">

The echo server binds port 2026 and sends your bytes back one time, with a listen backlog of 1. The client on <SlideLink session={7} page={8} /> prints port 8080, and the repo file uses 2026, so the printed pair cannot connect. The point still holds. The client sets a linger option of 1 and 0, so close sends RST in place of FIN, and the peer sees stage 6 die with no news about stage 5.

</Myth>

<Remember>

- The six stages in order: DNS lookup, TCP handshake, TLS handshake, request write, server processing, response read.
- DNS turns a name into an IP address. The handshake is SYN, SYN-ACK, ACK. TLS carries the certificate and the key exchange.
- Stage 4 is the moment your bytes leave your socket. Stage 5 is the server problem, and it becomes yours too. Stage 6 is bytes that arrive, or bytes that stop.
- A failure in stages 1 to 3 proves that no server saw the request.
- A 5xx admits a failure and stays silent about side effects.
- The new question on every status: will anything be different next time?
- 1xx interim. 2xx done. 3xx depends. 4xx usually not. 5xx usually yes.
- A linger option of 1 and 0 makes close send RST in place of FIN.

</Remember>

<Picture breaks="the machine tells you which case you are in. A network usually does not, so your code must classify first.">

A vending machine eats your coin and gives you nothing. You press the same button again. That is a retry: same slot, same button, same hope that the jam cleared. Now the screen reads "card expired". You take out a different card and tap it. That is not a retry, because you answered what the machine just told you with a new input.

The coin and the button are the method, the body and the headers that matter. The second card is a fresh token. People call both moves "trying again", and the machine treats them as two different events.

</Picture>

<KeyIdea id="same-request-or-a-new-one" title="A retry is the exact same step again">

Same method, same body, same headers that matter. You bet that the same action gives a different result, because you believe the failure was transient. The test is one sentence: with nothing changed and only a wait, is attempt 2 identical to attempt 1? A no means you are handling, not retrying.

</KeyIdea>

Three causes make that bet worth placing, and all three clear on their own: a network blink, a brief server overload, and a load balancer that picked an unhealthy backend.

Then classify, by nature and severity, before you touch a retry counter. <SlideLink session={7} page={15} /> gives four questions. Where did it fail, before a connection existed or after? Who admits fault, since a 5xx says "I failed" and a 4xx says "you failed"? Is the action idempotent, so does the same effect hold however many times it runs? And will a wait of 200 ms change anything?

Five answers mean stop, and <SlideLink session={7} page={16} /> lists them. A 404 resource that is not there now will not be there 200 ms from now, with one named exception that Part 4 gives. A failure before the handshake never reached a server, so the same broken path only burns the time twice. A geo-block refuses by policy, and no retry changes geography. A preflight failure, from CORS or from mixed content, means the client already refused and the real request never left. An outright auth failure needs a different credential.

Two families mean retry, because nothing was decided against you. Either the server admits fault, or the environment shifted under you. <SlideLink session={7} page={17} /> names eight members, and the list below holds them.

The last question is the dangerous one. GET, PUT and DELETE are idempotent, so a blind retry after a timeout is safe: reading twice changes nothing, setting X twice still gives X, and already gone stays already gone. POST is not, and charging the card twice means two charges. <SlideLink session={7} page={18} /> cites RFC 9110 section 9.2 for the method table, a callback to class 5.

<Myth myth="A token refresh plus the same call again is a retry with extra steps.">

The new Authorization header answers information the server just gave you, so the second call is a different request. Give it its own path in the code. A retry counter around a refresh hides a credential that is simply wrong, and then the client loops against the token endpoint for nothing.

</Myth>

<Myth myth="Auth failure is on the do-not-handle list, so the client gives up.">

The deck is careful here. An outright auth failure is not "do not handle it". It is "handle it with a token refresh", which is a different and valid flow. What a retry cannot fix is the same credential sent twice, because the same credential gives the same refusal.

</Myth>

<Myth myth="A POST must never be retried, because a retry can double-charge.">

The fix is not "do not retry". With no response you do not know whether the server finished the work, so a blind second attempt can double-execute. The fix makes the server able to tell that attempt 2 was attempt 1 again: the client sends an idempotency key, and the server checks it and deduplicates.

</Myth>

<Remember>

- A retry is the identical request again: same method, same body, same headers that matter.
- The test: with nothing changed and only a wait, is attempt 2 identical?
- The four questions: where did it fail, who admits fault, is it idempotent, is it transient?
- The five stop cases: 404, a failure before the handshake, a geo-block, a preflight refusal, an outright auth failure.
- The server-fault family: 500, 502, 503, 504, a connection timeout, a read timeout, a DNS server with no answer at all.
- The environment family: a network switch mid-flight, a CDN edge or load balancer that refuses, a cache not found, a TLS failure on a healthy host.
- GET, PUT and DELETE are idempotent. POST is not, so retry it after a timeout only with an idempotency key.

</Remember>

<Picture breaks="a child sees the crowd. A client sees only its own failure, so the random wait is the only coordination it gets for free.">

A school bell rings and 600 children run at one door that holds two at a time. Tell each child to push at most 5 times, so nobody stands there until dark. Tell each child to wait longer after each failed push, so the crowd thins. Then give each child a different random wait, or they all push on the same beat again and nothing changes. The fourth fix is not about the children. A teacher at the door says "this one is broken, use the other", and nobody even walks up until the teacher checks again.

The children are clients, the door is one upstream service, and the teacher is a circuit breaker.

</Picture>

<KeyIdea id="three-knobs-three-jobs" title="Three knobs, three different jobs">

Max attempts caps total damage, so a dead dependency fails in seconds and not forever. The exponential growth spaces the attempts out, so load on the upstream decays instead of holding steady. Full jitter decorrelates clients. Each knob fixes one of the three dangers, and none of them substitutes for another.

</KeyIdea>

The loop everyone writes first catches the timeout and continues at once, forever. <SlideLink session={7} page={20} /> shows it in four lines and names three dangers. No max count turns a permanently-down dependency into an infinite loop instead of a fast failure. No delay lets every client hammer the upstream at wire speed. No coordination across clients makes every retry loop fire on the same tick when the upstream recovers, which is the thundering herd.

The safe loop on <SlideLink session={7} page={21} /> is built live with the class. It takes a max of 5 attempts, a base of 0.2 s and a cap of 8.0 s. The delay is the smaller of the cap and the base times 2 to the attempt number, and then the real sleep is a uniform draw between zero and that delay. On the last attempt the loop raises instead of sleeping. The slide credits full jitter to AWS, 2015.

Some servers name the wait for you, and then their number wins. <SlideLink session={7} page={22} /> gives three codes. A 429 is a rate limit, so the server is fine and you ask too fast. A 503 often carries `Retry-After` during planned maintenance or load shedding. A 408 means the server gave up waiting for you to finish sending, and it rejected nothing about the request. Connection limits and interval caps of 5 or 10 seconds exist because clients that ignore the header can still overwhelm a server together.

The last control stops you asking a question whose answer you already have. A circuit breaker holds three states on <SlideLink session={7} page={23} />. CLOSED lets requests flow and counts failures. OPEN means the threshold broke, so requests fail instantly and locally with no call attempted at all. HALF-OPEN lets exactly one probe out after a cooldown: success closes the breaker, failure opens it again. Backoff protects an upstream from one client. A breaker protects it from a whole fleet, and it saves each caller the full timeout cost. The deck credits Nygard, "Release It!", 2007.

<Myth myth="Jitter means the delay plus or minus a little.">

Full jitter is a uniform draw between zero and the delay. A delay of plus or minus 10% keeps every client inside a narrow window around the same instant, so the herd only arrives a little wider. Without jitter, every client computes the same delay and retries in lockstep, which is the same herd, delayed.

</Myth>

<Myth myth="Your own backoff curve belongs on top of Retry-After.">

A server that hands you a number knows its own load better than your curve does. Honor the header and do not add your own delay on top of it. Trust the number over the curve, in both directions: a 30-second header beats your 0.8-second ceiling, and it also beats a longer one.

</Myth>

<Myth myth="A circuit breaker is a retry cap with a new name.">

It is the same idea one level up. A retry cap counts attempts inside one request, and the count dies with the call. A breaker counts failures per dependency, it remembers the verdict for a cooldown, and every caller shares that verdict. The state lives next to the dependency, which is the whole difference.

</Myth>

<Remember>

- The naive loop has three dangers: no max count, no delay, no coordination across clients.
- The live loop: max 5 attempts, base 0.2 s, cap 8.0 s. On the last attempt it raises instead of sleeping.
- The delay is the smaller of the cap and the base times 2 to the attempt. The sleep is a uniform draw from zero to it.
- With base 0.2 s and 5 attempts the sleep ceiling is 3.0 s, and the cap never binds.
- Full jitter comes from AWS, 2015. The breaker comes from Nygard, "Release It!", 2007.
- 429 is a rate limit and the server is fine. 503 often carries the header. 408 rejected nothing about your request.
- CLOSED counts failures. OPEN fails instantly and locally. HALF-OPEN lets one probe out.
- Backoff protects an upstream from one client. A breaker protects it from a fleet.

</Remember>

<Picture breaks="a projectionist can see the audience and the loop. A player sees only its own buffer, so its whole retry budget is a guess about human patience.">

A cinema runs a film from reels that arrive one by one from a depot. A little film sits in the loop, so the projectionist has a few seconds of slack before the screen goes dark. If a reel is late, asking the depot again may work. If the depot says "we are still printing that one", asking again in half a second is exactly right. If the projector cannot read this format, asking a hundred times changes nothing, and the fix is a different print. And if the lamp fails, no reel helps. You rebuild the projector.

The loop is the buffer, the depot is a CDN, the format is the codec, and the lamp is the media state of the device.

</Picture>

<KeyIdea id="switch-instead-of-retry" title="Retry asks the same source. Switch asks a different one">

A player fails silently, as a frozen frame or a spinner, and its retry budget is human: a viewer takes a few seconds of rebuffering, not a few minutes of correct exponential backoff. So many player failures want a different CDN, a lower bitrate or another rendition, and not the same request again.

</KeyIdea>

One play session makes hundreds of requests: a manifest, a key and dozens of segments, each with its own retry policy, on one timeline that a human watches. An API client can afford a long correct backoff. The player cannot, so timeouts differ by request type, and <SlideLink session={7} page={26} /> maps five network failures to a player answer.

Some failures are not network failures at all, and <SlideLink session={7} page={28} /> lists six fallbacks for them. A denied DRM key returns the same denial every time, so the player drops to a lower security level or a different key system. An unsupported codec means the device genuinely cannot decode this, so the player picks another rendition. A repeated child-manifest or segment failure escalates to a fatal coded error, not to an infinite loop. And iOS ResetMedia rebuilds the whole player pipeline, because that failure lives in device media state and not in a request.

Two last signals come from above the transport. Retry an entitlement check that times out, and never retry a clean "not entitled", because there the HTTP layer succeeded and the business layer decided. And read the response body, because it can say "degraded, use lower bitrate". Parts 1 to 3 used transport signals alone. A mature policy reads both layers.

<Myth myth="A 404 always means give up.">

The newest segment of a live stream can 404 for a real reason: the origin is still encoding it, or the CDN has not finished propagating it, and it will exist in a few hundred milliseconds. The fix is a short bounded retry of 2 or 3 attempts with a small fixed delay, for live-edge segment requests and nowhere else. A 404 on an on-demand asset still means give up.

</Myth>

<Myth myth="Real deployments only use the status codes in the registry.">

Players meet 419, 474 and 475, which no RFC defines. A 419 marks token or session expiry, so handle it like auth. The 474 and 475 codes appeared when a retried segment came back as a mismatched partial result. The lesson is not the numbers. Your own codes owe a caller the same two facts: what the condition means, and whether it is retryable.

</Myth>

<Remember>

- A player fails silently, as a frozen frame or a spinner. An API client fails visibly.
- One session makes hundreds of requests: a manifest, a key, and dozens of segments, each with its own policy.
- The retry budget is human: seconds of rebuffering, not minutes of backoff.
- A network switch changes the IP mid-download, so the request is dead, not slow.
- A multi-CDN player switches CDN instead of retrying the same dead edge.
- The one 404 exception: the newest live segment, 2 or 3 attempts, a small fixed delay, nowhere else.
- Fallbacks, not retries: a denied DRM key, an unsupported codec, a broken device media state.
- 419 is token or session expiry. Document your own codes the same way.
- Retry an entitlement check that times out. Never retry a clean "not entitled".
- The response body can carry the signal, not only the status line.

</Remember>

<Picture breaks="bread carries a visible date and a stale cache does not, unless the cache says so.">

A town has one bakery and the oven breaks. A shop with no plan puts up a "closed" sign. A shop with a plan sells yesterday's bread, marked as yesterday's, and most people buy it. When the oven comes back, a worse problem starts. Everyone who walked away in the morning returns inside the same ten minutes, and the oven is still warming up. The fix is not more bread. It is to let people in at a steady rate, and to tell them different times to return.

Yesterday's bread is a stale cache copy, the sign is an error page, and the warming oven is a recovering service at a fraction of its capacity.

</Picture>

<KeyIdea id="answer-with-something-worse" title="Answer smaller, not nothing">

A system that can answer with slightly-wrong data survives outages that a system demanding perfectly-fresh-or-nothing does not. Three levers do it: failover to a backup, a feature flag that turns off the expensive part, and graceful degradation that answers smaller.

</KeyIdea>

On 8 June 2021 about 85% of the Fastly network returned errors. Detection took about 1 minute, and 95% recovered took 49 minutes. <SlideLink session={7} page={31} /> reopens the closing question of class 6. Today's edge survives your origin dying, because a cache can serve a stale hit. So what happens when the edge, or a whole region, is the thing that dies? The `stale-if-error` directive of RFC 5861 points the same idea the other way, and keeps the last good copy in service when the cache cannot reach the origin.

Three levers sit above that. Failover trips a breaker OPEN on the primary and routes to a backup: a different region, provider or CDN. A feature flag disables a non-essential feature, such as recommendations, to shed load off playback itself, with no deploy and in seconds. Graceful degradation answers smaller, with a lower bitrate or a slightly stale price instead of a spinner. Every case study of the class has one lever.

Then plan the recovery. Every client that was retrying, backing off or waiting on a cooldown now tries again, and their schedules line up because they all started failing at the same moment. The recovering service runs at 1% of capacity while it warms caches, and it gets close to 100% of normal traffic in its first reachable second. <SlideLink session={7} page={33} /> names three mitigations: jitter, staggered half-open probes, and slow start on the recovering side.

<Myth myth="stale-if-error is a kind of retry inside the cache.">

It is not a retry at all. It changes the answer, not the attempt. The cache decides to serve something known-stale rather than nothing. The generalization reaches past caches, and it is the one line to carry out of this part.

</Myth>

<Myth myth="The failure is the most dangerous moment of an incident.">

The recovery is. At the failure the load drains away. At the recovery it all arrives at once, in lockstep, against a cold server. That is why jitter, staggered probes and a server-side ramp belong in the design before the incident, and not in the postmortem after it.

</Myth>

## The task, and the question it leaves open

<SlideLink session={7} page={35} /> sets one practice task for the week, due before class 8. Take a client you already have and put it behind a resilient-call wrapper that you write from scratch. The checklist of the slide, and nothing past it:

- Classify the failure as retryable or not, by the rules of this class.
- Back off with full jitter, capped at a max attempt count.
- Honor a `Retry-After` header when the server sends one.
- Open a circuit after N consecutive failures to one dependency, and fail fast while it is open.
- Write the test server too, with three routes: `/sometimes-500`, which fails a configurable fraction of the time, `/always-503-with-retry-after`, and `/always-down`.
- Hand in the wrapper, the test server, and a log or plot of request timestamps under each mode. It must show the backoff curve, the circuit opening, and the circuit closing again.

The homework list adds five more items and asks for at least one. The fifth is the one to do if you do only one. A hint ladder of questions sits in <ModuleLink id="s07-m08-build-the-wrapper" />, and no page here gives a solution.
